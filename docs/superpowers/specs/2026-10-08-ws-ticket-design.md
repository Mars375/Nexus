## 0. Constat

- `/api/ws` (`live.py:live_updates`) ne contrôle que `Origin` (`origin_allowed`, un `Origin` absent passe) ; `HostCheckMiddleware` contrôle `Host` avant lui. Aucun jeton : le flux (références `nx-task-…`, `nx-evt-…`, `kind`, curseurs, `instance`) est lisible par quiconque atteint le port avec un `Host` admis.
- `Settings.__post_init__` refuse tout `NEXUS_HOST` hors de `localhost`, `127.0.0.1`, `::1` (renvoi à #57). `nexus` et `nexus-dev` appellent `uvicorn.run(host=…)` sur **une** valeur, `access_log=False`, `uvicorn_log_config()`. Avec `localhost`, uvicorn passe le nom à `loop.create_server`, qui ouvre une socket par réponse de `getaddrinfo` : en général deux (`127.0.0.1` et `::1`), selon la résolution du système.
- `uvicorn[standard]` choisit `websockets_sansio_impl`. Au niveau INFO, uvicorn écrit `"WebSocket %s"` avec **le chemin et la requête** (`get_path_with_query_string`) ; `WebSocketPathFilter` en retire la requête. **Au niveau DEBUG**, websockets 17 écrit en plus sur `uvicorn.error` la ligne de requête complète (`< GET /api/ws?… HTTP/1.1`) et **chaque en-tête reçu** (`< %s: %s`, `websockets/server.py:631`), puis chaque en-tête envoyé, et enfin chaque trame reçue (`"< %s"`, `websockets/protocol.py:609`) et envoyée (`"> %s"`, `protocol.py:755`), contenu compris : le `hello` porte le curseur. Aucun filtre ne couvre ces lignes aujourd'hui. Au même niveau, une poignée de main que websockets refuse lui-même (par exemple `Sec-WebSocket-Protocol: nexus.live.v1 nxw_…`, une espace au lieu d'une virgule) lève `InvalidHeaderFormat` dans `ServerProtocol.accept`, qui écrit `"! invalid handshake"` avec `exc_info=True` (`websockets/server.py:199`, dans le bloc `except InvalidHandshake` des lignes 195-199) : le message de l'exception recopie la valeur de l'en-tête (« expected comma at 14 in nexus.live.v1 nxw_… », vérifié), donc la trace aussi. uvicorn répond alors 400 sans appeler l'application : le ticket n'est pas consommé. **À tout niveau de journal**, le corps de ce 400 recopie le même message (`"Failed to open a WebSocket connection: …"`, `websockets/server.py:200-207`), donc le ticket, à l'expéditeur : exception à ADR-006 acceptée par Loïc le 2026-10-13 (§3.6). **Au niveau TRACE**, `Config.load` enveloppe l'application dans `MessageLoggerMiddleware` (`uvicorn/config.py:541-542`), qui écrit sur `uvicorn.asgi` `"Started scope=%s"` avec tout le scope : seuls `headers` et les corps y sont remplacés, `subprotocols` (donc le ticket) et `query_string` (le curseur) passent tels quels.
- Côté interface, `liveUpdates.ts` ouvre `new WebSocket(url)` sans protocole ; `live.ts:connectLive` reconnecte avec backoff (0,5 s à 10 s, ±20 %), déclare `unknown` après 30 s, coupe après 45 s de silence. L'application reste montée sous l'écran verrouillé et la connexion temps réel continue (`App.tsx`).
- Le proxy Vite vise `http://127.0.0.1:${NEXUS_PORT}` en dur (`vite.config.ts`), sans `changeOrigin` : `Host: localhost:5173` et `Origin: http://localhost:5173` arrivent au serveur. Ses erreurs WebSocket ne journalisent que la pile (`ws proxy error:`), pas l'URL ; ses erreurs HTTP journalisent l'URL.
- Le `live_instance` est déjà tiré **par processus** (`app.py`) : Nexus suppose déjà un seul processus serveur.
- SECURITY §9 dit « Nexus ne fera jamais : exposer une surface d'administration hors de la machine locale » ; §5 « lecture distante uniquement » ; ARCHITECTURE §3.4 « pas d'exposition publique ». Écouter sur le tailnet touche ces trois phrases (D1).

## 1. Modèle de menace

**Ce qui change en écoutant sur le tailnet.** Le port devient joignable par tout appareil du tailnet que les ACL Tailscale laissent passer : les nœuds (Helios, Cortex, Synapse, Artémis), les autres appareils de Loïc, et tout appareil partagé ou nœud compromis. Le trafic qui passe par Tailscale est chiffré de bout en bout par WireGuard : HTTP en clair sur le tailnet ne s'expose pas au réseau local traversé (Wi-Fi). Le REST est déjà fermé par jeton (ADR-020) ; le WebSocket est la seule surface de données encore ouverte. Ce qu'il livre (références, types, curseurs, rythme d'activité) est peu, mais c'est de la donnée interne (SECURITY §2) : elle ne doit pas sortir de la machine sans authentification.

**Écouter sur `100.x` ne veut pas dire n'être joignable que par Tailscale.** Le bind choisit l'adresse de destination, pas l'interface d'arrivée.
- **Linux** applique le modèle d'hôte faible : une socket liée à `100.101.102.103` accepte un paquet destiné à cette adresse arrivé par `wlan0` ou `eth0`. Un pair du réseau local qui ajoute une route vers `100.101.102.103` par la machine Nexus atteint le port **en clair, sans WireGuard ni ACL Tailscale**. `rp_filter` n'y change rien : la source du pair est joignable par l'interface d'arrivée. La règle de Tailscale qui jette les sources `100.64.0.0/10` arrivant hors de `tailscale0` ne couvre pas ce cas, car la source est une adresse du réseau local. Parade documentée dans SECURITY §3 par la PR B, **recommandée et non imposée par le code** (décision de Loïc, 2026-10-13) : une règle de pare-feu qui n'accepte le port que sur `tailscale0` et `lo`. L'exemple vit dans une table à lui. Il ne suppose donc ni table `inet filter` ni chaîne `input` existantes, et ne dépend pas de l'ordre de leurs règles : dans nftables, un `accept` d'une chaîne de base laisse le paquet passer aux autres chaînes de base du même point d'accroche, alors qu'un `drop` est définitif. Un `nft add rule` ajouté en fin de chaîne, lui, ne verrait jamais un paquet déjà accepté plus haut. Le port est celui de `NEXUS_PORT` :
  ```sh
  NEXUS_PORT=8765   # la valeur configurée pour Nexus
  nft -f - <<EOF
  add table inet nexus
  flush table inet nexus
  table inet nexus {
    chain input {
      type filter hook input priority filter; policy accept;
      tcp dport $NEXUS_PORT iifname != { "lo", "tailscale0" } drop
    }
  }
  EOF
  ```
  Le script se rejoue sans doublon : `add table` crée la table si elle manque, `flush table` en vide les règles, et le tout s'applique dans une seule transaction. Sans ces deux lignes, chaque `nft -f` ajoute une seconde règle `drop` identique (vérifié avec nftables 1.0.9, dans un espace de noms réseau jetable : trois passages laissent une seule règle, contre deux règles après deux passages de l'ancien script). Écartée : commencer par `destroy table inet nexus`, qui exige nftables 1.0.8 ou plus et un noyau qui connaît `destroy`, sans gain ici. `iifname` (et non `iif`) admet une interface absente au chargement de la règle, comme `tailscale0` avant le démarrage de Tailscale. `lo` reste nécessaire, car une connexion locale vers sa propre adresse `100.x` passe par `lo`. SECURITY dit aussi comment rendre la table persistante (fichier inclus par `/etc/nftables.conf`).
- **Windows** (Helios, l'hôte de Nexus) applique par défaut le modèle d'hôte fort en réception, d'après la documentation de Microsoft (« Strong and Weak Host Models », The Cable Guy, depuis Windows Vista et Server 2008). Ce n'est **pas** vérifié sur Helios, et la documentation fait une exception pour une interface où `WeakHostReceive` ou le routage (`Forwarding`) est activé. Le partage de connexion (ICS), Hyper-V ou WSL, ou Tailscale en routeur de sous-réseau ou nœud de sortie peuvent activer le routage. Le contrôle sur Helios (`Get-NetIPInterface | Select-Object InterfaceAlias,AddressFamily,Forwarding,WeakHostReceive`) **reste à faire, et rien n'attend son résultat** (Loïc, 2026-10-13) : la règle de pare-feu est recommandée dans tous les cas. Il fait partie des contrôles à faire sur Helios, regroupés au §2 (compléments).
  - Règle recommandée : une règle entrante limitée au port de `NEXUS_PORT` et à l'interface Tailscale, sur tous les profils, car l'interface Tailscale n'a pas forcément le profil du réseau de la maison : `New-NetFirewallRule -DisplayName "Nexus (tailnet)" -Direction Inbound -Protocol TCP -LocalPort <NEXUS_PORT> -InterfaceAlias Tailscale -Profile Any -Action Allow`. La boucle locale n'est pas filtrée par le Pare-feu Windows.
  - **Piège de la première écoute.** Quand `python.exe` écoute pour la première fois, Windows propose d'autoriser le programme, avec le profil **Privé coché par défaut**. Accepter crée une règle « python.exe » qui autorise tout port, sur toute interface classée Privé. Si le Wi-Fi de la maison est classé Privé, cette règle ouvre le port au réseau local et annule la restriction par interface. Cliquer « Autoriser » avec Privé seul coché crée **aussi** des règles qui **bloquent** `python.exe` sur le profil Public (TCP et UDP). Si l'interface Tailscale est classée Public, ces règles l'emportent sur « Nexus (tailnet) » et ferment le tailnet : dans le Pare-feu Windows, une règle de blocage l'emporte sur toute règle d'autorisation. SECURITY dit donc de lister après le premier lancement **toutes** les règles entrantes qui visent `python.exe`, qu'elles autorisent ou bloquent (`Get-NetFirewallRule -Direction Inbound | Where-Object { ($_ | Get-NetFirewallApplicationFilter).Program -like '*python*.exe' } | Select-Object DisplayName,Action,Profile,Enabled`, sans filtre `-Action`), et de les désactiver toutes (même commande, terminée par `| Disable-NetFirewallRule`). Il ne faut pas les remplacer par une règle qui bloque `python.exe` : elle fermerait aussi le tailnet. Pour la même raison, fermer l'invite par « Annuler », qui crée des règles de blocage du programme, est à éviter. **À vérifier sur Helios** (non vérifiable ici) : les règles exactes que crée l'invite (actions, profils, protocoles) et le profil de l'interface Tailscale (`Get-NetConnectionProfile -InterfaceAlias Tailscale`).
- Les jetons et les tickets protègent toujours les données : un pair qui passe ainsi n'obtient rien sans jeton. Le risque est d'abord l'exposition du port au réseau local, et un jeton envoyé par ce chemin (client mal configuré) circulerait en clair.

## 2. Décisions (validées par Loïc le 2026-10-08, compléments le 2026-10-13)

**D1 — Portée de l'exposition.** Nexus peut écouter sur le tailnet de Loïc, jamais sur un réseau local ni sur Internet.
- (a) **Recommandé :** tailnet seulement. SECURITY §9 devient « exposer une surface hors de la machine locale et du tailnet de Loïc » ; §5 précise que les nœuds **écrivent** dans Nexus par l'API (ADR-015), ce qui n'est pas une mutation croisée ; ARCHITECTURE §3.4 cite le tailnet. Recommandation de doc : une règle d'ACL Tailscale qui limite le port 8765 aux appareils de Loïc et aux nœuds.
- (b) Tailnet et réseau local (192.168.x) : rien ne le demande, et le Wi-Fi traversé verrait les jetons en clair (pas de TLS).
- (c) Garder la boucle locale pour toujours : #57 se réduit au ticket, les agents des autres nœuds ne publient jamais d'événement.

**D2 — Transport du ticket à la poignée de main.**
- (a) **Recommandé :** `Sec-WebSocket-Protocol`. Le client offre deux sous-protocoles, `new WebSocket(url, ['nexus.live.v1', ticket])` ; le serveur exige exactement ces deux entrées et accepte avec `subprotocol="nexus.live.v1"`, **jamais** le ticket en écho (Chrome rejette une poignée de main qui n'en renvoie aucun quand le client en a offert). Les caractères base64url et `_` sont des `token` HTTP valides. Aucun journal d'uvicorn ni de Vite n'écrit d'en-tête au niveau INFO ; la console de Chrome n'écrit que l'URL. C'est le schéma de Kubernetes (`base64url.bearer.authorization.k8s.io.…`).
- (b) Paramètre de requête `?ticket=` : le plus simple, mais l'URL est ce que tout le monde journalise (uvicorn, proxies, console du navigateur, traces Playwright) ; on dépendrait de `WebSocketPathFilter` pour chaque nouvelle ligne, contre la règle « jamais de requête reçue dans un journal » (checklist §1).
- (c) Premier message après `accept` : écarté par le critère d'acceptation (refus **avant** `accept`).
- (d) Cookie : écarté par ADR-020 D4 (Tauri, CSRF).

**D3 — Format et durée de vie.**
- (a) **Recommandé :** `nxw_` + 43 caractères base64url (32 octets de `secrets.token_bytes`), même forme que `nxt_` pour réutiliser la validation stricte ASCII. TTL **30 s** : couvre une requête REST lente (10 s de délai) puis l'ouverture, sans laisser de fenêtre utile à un vol. Motif `nxw_` ajouté à `nexus/secrets.py` (un ticket collé dans un commentaire est masqué). Pas de règle `.gitleaks.toml` : un ticket vit 30 s et n'est jamais écrit dans un fichier.
- (b) TTL 10 s : plus court, mais une requête de ticket lente (proxy Vite, machine chargée) échoue sans raison visible.
- (c) TTL 60 s ou 128 bits : sans gain.

**D4 — Stockage.**
- (a) **Recommandé :** en mémoire, dans le processus (`app.state.ws_tickets`, classe `TicketStore`), indexé par l'empreinte SHA-256 du ticket (comme `actor_tokens.token_hash` : un vidage mémoire ou un `repr` ne livre aucun ticket utilisable). Un redémarrage efface les tickets : le client en redemande un, comme il le fait déjà après chaque coupure. **Pas de migration.** Au plus 16 tickets en attente par jeton : le 17ᵉ évince le plus ancien (pas d'erreur, l'interface n'en garde jamais plus d'un). Les tickets périmés sont purgés à chaque émission et consommation.
- (b) Table SQLite `ws_tickets` (migration `0006`, `UPDATE … WHERE used_at IS NULL` atomique) : survit au redémarrage et à plusieurs processus, mais impose une migration, une écriture par connexion et un nettoyage, pour un objet de 30 s. La PR ne serait plus fusionnable par l'agent.

**D5 — Liaison du ticket et contenu du flux.**
- (a) **Recommandé :** le ticket est lié au **jeton** qui l'a demandé (`token_id`, `actor`). À la consommation, le serveur relit la ligne `actor_tokens` : un jeton révoqué entre l'émission et l'usage fait refuser le ticket. Le flux **n'est pas filtré par acteur** : la matrice appliquée (SECURITY §3) donne la lecture de tout à tout acteur authentifié, et le WebSocket ne livre que ce que les `GET` livrent déjà. L'acteur est gardé pour la révocation (D6) et pour un futur périmètre (Artémis, v2, ADR-008).
- (b) Filtrer le flux par acteur : aucune règle de lecture par acteur n'existe à appliquer.

**D6 — Révocation pendant une connexion ouverte.**
- (a) **Recommandé :** la boucle `push` relit `actor_tokens.revoked_at` par clé primaire dans la même session que `changes_since` (une lecture indexée de plus toutes les 250 ms) ; un jeton révoqué **ou une ligne absente** (supprimée de la base) ferme la socket avec le code **4401** et la raison fixe « jeton révoqué ». La même règle vaut à la consommation du ticket (§3.3) : une ligne absente vaut révocation. Effet en moins de 0,25 s, cohérent avec « une révocation vaut à la requête suivante » (ADR-020 D2).
- (b) Relire toutes les 15 s, au rythme du `ping` : moins de lectures, révocation tardive.
- (c) Ne rien relire : une socket ouverte avant la révocation reste ouverte jusqu'à sa fin, sans limite.

**D7 — Codes de refus.**
- (a) **Recommandé :** avant `accept`, tout refus (sous-protocoles absents ou mal formés, ticket inconnu, périmé, déjà utilisé, jeton révoqué, `Origin` étrangère, curseur invalide) est une fermeture **1008 sans raison distinctive** ; uvicorn la transmet en HTTP 403, que le navigateur ne voit que comme une fermeture 1006. Les cas sont indiscernables : aucun oracle sur l'existence d'un ticket. Après `accept` : **4401** pour la révocation (D6), les codes existants pour le reste. Le refus de curseur porte aujourd'hui `reason="curseur invalide"` (`live.py:173`) : la PR A le retire, et tout refus avant `accept` devient `close(code=1008)` sans raison. Sur un vrai serveur, uvicorn jette déjà la raison (`reject(403, "")`, `websockets_sansio_impl.py:462-475`), mais `TestClient` la montre : elle serait le seul refus discernable, et il révélerait qu'un ticket valide vient d'être brûlé. L'interface n'a pas besoin de distinguer : elle redemande un ticket, et c'est la requête REST qui dit 401.
- (b) Réponses HTTP distinctes à la poignée de main (extension ASGI `websocket.http.response`, 401 vs 403) : utile à une CLI, invisible au navigateur, et crée l'oracle évité en (a).

**D8 — Clients hors navigateur (CLI, agents).**
- (a) **Recommandé :** le ticket seulement. Un agent fait `POST /api/ws-ticket` avec son jeton, puis ouvre le WebSocket avec les mêmes sous-protocoles (`websockets.connect(uri, subprotocols=["nexus.live.v1", ticket])`). Un seul chemin d'authentification à tester. `demo_agent` n'utilise pas le WebSocket : rien à changer.
- (b) Accepter aussi `Authorization: Bearer` à la poignée de main : plus simple pour une CLI, mais deux chemins, et websockets écrit `Authorization` au niveau DEBUG.

**D9 — Valeurs admises pour `NEXUS_HOST`.**
- (a) **Recommandé :** la boucle locale (`127.0.0.1`, `localhost`, `::1`, comme aujourd'hui) et les **adresses IP littérales** des plages Tailscale : `100.64.0.0/10` (IPv4) et `fd7a:115c:a1e0::/48` (IPv6). Refusés : `0.0.0.0`, `::` et toute adresse joker, tout nom DNS (hors `localhost`), toute autre plage (LAN, publique), une adresse avec port, crochets, zone (`%eth0`, y compris `fd7a:115c:a1e0::1%eth0` : `ipaddress` l'accepte avec `scope_id = "eth0"` et la dit dans `fd7a:115c:a1e0::/48`, vérifié ; le refus teste donc `scope_id` explicitement), forme IPv4 dans IPv6 (`::ffff:100.64.0.1`), chiffres non ASCII ; message générique, sans recopier la valeur (ADR-006). Limite : `100.64.0.0/10` est aussi l'espace CGNAT des opérateurs ; un partage de connexion mobile peut donner une telle adresse hors Tailscale. La plage seule ne suffit donc pas : voir le complément ci-dessous.
- **Complément décidé par Loïc le 2026-10-13 : contrôle obligatoire auprès de Tailscale.** Avant d'ouvrir l'écoute du tailnet, au démarrage et à chaque reprise, Nexus vérifie que Tailscale est connecté (état `Running`) et que l'adresse configurée fait partie des adresses qu'il a données à ce nœud (`tailscale status --json --peers=false`), et il refait ce contrôle à chaque tour tant que l'écoute est servie. Tailscale pas connecté, adresse absente, commande en échec ou trop lente : pas de bind, avertissement une fois par changement d'état, nouvel essai 30 s plus tard. Commande précisée après la quatrième relecture : `tailscale ip`, prévu d'abord, rend encore l'adresse quand Tailscale est arrêté ou que sa clé a expiré (§3.7). La boucle locale n'est jamais concernée. Mécanisme, cas limites et ce que le contrôle ne prouve pas : §3.7. C'est l'option (c) sous une forme qui ne lie que l'écoute du tailnet au binaire Tailscale : sans Tailscale, Nexus démarre quand même sur la boucle locale.
- (b) Toute adresse littérale sauf joker : plus souple, mais un `192.168.x` expose Nexus au Wi-Fi, en clair.
- (c) (a) plus vérification au démarrage que l'adresse appartient à Tailscale (même binaire `NEXUS_TAILSCALE_BIN` que `nodes`, qui appelle `tailscale status --json`) : lève l'ambiguïté CGNAT, mais lie le démarrage au binaire Tailscale. Retenue le 2026-10-13 sous la forme du complément ci-dessus.

**D10 — Boucle locale et tailnet ensemble.** Une écoute sur la seule adresse du tailnet casse l'interface locale (le proxy Vite vise `127.0.0.1` en dur) et empêche Nexus de démarrer si Tailscale n'est pas encore lancé (démarrage automatique, Tauri).
- (a) **Recommandé :** `NEXUS_HOST` devient une liste (`127.0.0.1,100.101.102.103`) : au plus une adresse de boucle locale et une adresse du tailnet ; la boucle locale est toujours écoutée (`localhost` compte pour une entrée et ouvre `127.0.0.1` et `::1`, §3.7). `nexus` ouvre une socket par adresse et les sert par **un seul** `uvicorn.Server`, dans une coroutine à lui (§3.7). L'écoute du tailnet part « en attente » : son premier contrôle et son premier bind ont lieu dans la tâche de surveillance, juste après le démarrage, pour que Tailscale ne retarde jamais la boucle locale (§3.7). Si l'adresse du tailnet n'est pas confirmée par Tailscale (D9, complément) ou pas disponible au démarrage, Nexus journalise un avertissement (sans l'adresse) et sert la boucle locale seule. **Reprise (demandée par Loïc) :** tant que la socket du tailnet manque, Nexus retente toutes les 30 s le contrôle puis le bind, et ajoute la socket au serveur dès que Tailscale confirme l'adresse et que le bind réussit, sans redémarrage (mécanisme : §3.7, sans second serveur ni seconde configuration) ; une coupure de Tailscale pendant le service ne touche jamais la boucle locale. Le succès de la reprise est journalisé une fois, sans l'adresse. Après le succès, la même tâche continue de surveiller l'écoute et refait le contrôle à chaque tour : si la boucle d'événements la perd en service (adresse retirée par un redémarrage de Tailscale, erreur d'acceptation sous Windows, §3.7) ou si Tailscale ne confirme plus l'adresse, l'écoute repasse « en attente » et la reprise recommence, toujours sans redémarrage. Si la tâche s'arrête sur une erreur imprévue, elle ferme d'abord l'écoute du tailnet si elle est ouverte : une écoute qui n'est plus contrôlée n'est plus servie (§3.7). **Boucle locale (décidé par Loïc le 2026-10-13) :** la même tâche surveille aussi les écoutes de boucle locale et reprend de même une écoute perdue en service, sans contrôle Tailscale ; au démarrage, un échec de bind de la boucle locale reste fatal. Chaque échec de reprise est journalisé en WARNING une fois par changement d'état (§3.7). `nexus-dev` (rechargement automatique, une seule socket) reste limité à la boucle locale.
- (b) Une seule adresse : l'utilisateur local passe aussi par l'adresse du tailnet (nouvelle variable pour la cible du proxy Vite) ; Nexus est injoignable, même en local, quand Tailscale est arrêté.
- (b′) Surveiller et reprendre le tailnet seul, et laisser une écoute de boucle locale perdue jusqu'au redémarrage : écarté par la décision de Loïc du 2026-10-13, car le défaut de la boucle proactor (§3.7) frappe aussi la boucle locale, et l'interface locale disparaîtrait sans redémarrage.
- (c) Comme (a), mais refus de démarrer si l'adresse du tailnet manque : plus visible, mais Nexus disparaît pour une panne qui n'est pas la sienne (ARCHITECTURE §6).

**D11 — Couplage avec `NEXUS_ALLOWED_HOSTS`.**
- (a) **Recommandé :** les adresses IP de `NEXUS_HOST` sont admises d'office dans le contrôle de `Host` (forme normalisée de `hosts.normalize_host`) : un `Host` littéral égal à l'adresse d'écoute ne peut pas venir d'un DNS rebinding. Un nom MagicDNS (`helios.<tailnet>.ts.net`) reste à déclarer dans `NEXUS_ALLOWED_HOSTS`.
- (b) Exiger que chaque adresse non loopback de `NEXUS_HOST` figure aussi dans `NEXUS_ALLOWED_HOSTS`, sinon refus de démarrer : explicite, mais c'est une configuration en double qui ne protège de rien.

**D12 — Découpage.**
- (a) **Recommandé :** deux PR après celle de cette conception (§6). Le ticket exigé et son envoi par l'interface vont ensemble : les deux appelants (interface, tests) sont dans ce dépôt, et un ticket « accepté s'il est présent » serait un contournement temporaire sans appelant externe à ménager.
- (b) Trois PR à la manière d'ADR-020 D7 (ticket accepté, puis envoyé, puis exigé) : une fenêtre où le WebSocket reste ouvert sans ticket, pour aucun appelant externe.

## 3. Conception détaillée (sous les recommandations)

### 3.1 Émission : `POST /api/ws-ticket`

- Route du routeur de `live.py`, dépendance `authenticated_token` (nouvelle, dans `auth/deps.py`, qui rend `(token_id, actor)` ; `authenticated_actor` reste et s'appuie dessus ; `tokens.lookup` gagne une variante qui rend la ligne). Mêmes refus qu'ailleurs : 401 `auth_required`, 401 `invalid_token`, 403 `actor_mismatch` (D8, D9 d'ADR-020).
- Pas de corps attendu. Réponse `200` : `{"ticket": "nxw_…", "protocol": "nexus.live.v1", "expires_in": 30}`, en-tête `Cache-Control: no-store`. Ce n'est pas une entité de `nexus.db` : ni `source` ni `measured_at` (le contrat de provenance ne parcourt que les `GET`).
- Le journal d'accès écrit `POST /api/ws-ticket 200 1 ms`, jamais le corps.

### 3.2 `TicketStore` (`server/src/nexus/auth/tickets.py`)

- `issue(token_id, actor) -> str`, `consume(ticket) -> Grant | None` (`Grant` : `token_id`, `actor`). Horloges injectables pour les tests : `monotonic` (défaut `time.monotonic`) et `wall` (défaut `time.time`, secondes UTC depuis l'époque). **Pas `nexus.clock.now`** : il rend des `datetime` de même `ZoneInfo("Europe/Paris")`, et Python soustrait deux `datetime` de même `tzinfo` sans tenir compte du décalage. Au passage à l'heure d'hiver (25/10/2026, 03:00 CEST → 02:00 CET), un ticket émis à 00:59:50 UTC et présenté à 01:00:05 UTC donnerait −59 min 45 s (vérifié), donc un recul et un refus à tort ; au passage à l'heure d'été, un faux saut d'une heure.
- Une entrée garde l'empreinte, `token_id`, `actor`, l'instant monotone et l'instant mural d'émission. Périmée si `monotonic() - m0 >= 30` **ou** si l'horloge murale a avancé de 30 s ou plus ou reculé (veille : `CLOCK_MONOTONIC` de Linux s'arrête pendant la mise en veille, l'horloge murale non). La borne exacte (30,000 s) est refusée.
- `consume` vérifie la forme (`is_well_formed`, `nxw_`) avant tout hachage, puis fait le `pop` de l'empreinte sous un `threading.Lock` (l'émission tourne dans le pool de threads de FastAPI, la consommation dans la boucle asyncio : un `asyncio.Lock` ne suffirait pas). Le ticket est retiré **même s'il est périmé**. La recherche est un accès de dictionnaire par empreinte : le temps qu'elle prend ne renseigne que sur une empreinte, pas sur le ticket.

### 3.3 Poignée de main (`live.py:live_updates`)

Ordre, chaque refus étant une fermeture 1008 avant `accept`, sans raison qui recopie quoi que ce soit :
1. `Host` (middleware, inchangé).
2. `Origin` (inchangé ; le commentaire « client non navigateur, local » devient « client non navigateur : il lui faut quand même un ticket »). Refusé ici, le ticket **n'est pas consommé**.
3. Sous-protocoles : exactement deux entrées, `nexus.live.v1` et un ticket bien formé, sans doublon ; sinon refus.
4. `consume(ticket)` sous verrou ; puis relecture de `actor_tokens` par `token_id` (`asyncio.to_thread`) : révoqué ou ligne absente, refus.
5. Curseur (`start_cursor`, inchangé). Refusé ici, le ticket est déjà brûlé : l'usage unique ne dépend d'aucune autre condition. La fermeture perd sa raison « curseur invalide » (D7).
6. `accept(subprotocol="nexus.live.v1")`, puis `hello` (inchangé).

**Un seul processus.** Les tickets, comme `live_instance`, vivent dans le processus. Nexus se lance par `nexus` (un processus), `nexus-dev` (un processus de travail, relancé au rechargement : les tickets en cours sont perdus, le client en redemande) ou le sidecar Tauri. Lancer uvicorn avec `--workers` n'est pas pris en charge : ARCHITECTURE §3.3 l'écrit.

### 3.4 Connexion ouverte

`read_changes` relit aussi `ActorToken.revoked_at` du `token_id` dans la même session ; révoqué ou ligne absente, `push` ferme avec 4401 « jeton révoqué » et s'arrête. Les messages ne changent pas (références, types, curseurs).

### 3.5 Interface

- `web/src/api.ts` : `liveApi.ticket(signal)` = `request<{ticket, protocol, expires_in}>('/api/ws-ticket', { method: 'POST', signal })` ; la réponse est validée (forme `nxw_`, `protocol` attendu) avant usage. Un 401 passe par le chemin existant de `request()` : oubli du jeton refusé et écran « Nexus verrouillé », **seulement si** le jeton envoyé est encore celui du stockage (voir plus bas le 401 sans verrouillage).
- `web/src/live.ts` : `connectLive` reçoit `ticket: (signal: AbortSignal) => Promise<string>` et `open: (url, protocols) => LiveSocket`. **Avant chaque connexion et chaque reconnexion**, il demande un ticket neuf, ne le garde pas et ne le réutilise jamais. L'URL ne change pas (curseur et `instance` seulement). Le délai de silence (45 s) est armé avant la demande de ticket : une demande qui n'aboutit pas compte comme une poignée de main qui n'aboutit pas.
- Échec de la demande : 401 → aucune socket. Ensuite, selon `getAuthState().locked` **lu après** le 401 :
  - verrouillée : aucune nouvelle tentative tant que l'application l'est (plus de boucle de 401 toutes les 10 s) ; au déverrouillage (`markUnlocked`, `onUnlockedElsewhere`), connexion immédiate avec `attempt` remis à zéro ;
  - **pas verrouillée** : `request()` n'oublie le jeton et ne verrouille que si le jeton envoyé est encore celui du stockage (`api.ts:167`, `getToken() === sent`). Un 401 sans verrouillage veut donc dire que le jeton a changé entre-temps (autre onglet) : backoff existant (`attempt` + 1), et la demande suivante part avec le nouveau jeton. Attendre un déverrouillage qui ne viendra pas couperait le temps réel pour de bon.
- Erreur réseau, délai dépassé ou 5xx sur la demande de ticket → backoff existant (`attempt` + 1).
- `stop()` pendant la demande : la requête est annulée (`AbortController`) et aucune socket n'est ouverte ; une réponse tardive est ignorée.
- Fermeture 4401 ou toute autre perte : chemin de reconnexion habituel ; la demande de ticket qui suit reçoit le 401 et verrouille. Le ticket n'est jamais affiché ni écrit dans la console par le code de l'interface.
- Tauri : `new WebSocket(url, protocols)` fonctionne dans WebView2 ; `NEXUS_ALLOWED_ORIGINS` et le CORS de #47 restent nécessaires pour une interface distante (hors de #57).

### 3.6 Journaux

- Nouveau filtre dans `nexus/logs.py`, ajouté par `uvicorn_log_config()` à chaque gestionnaire comme `WebSocketPathFilter`. Un filtre de gestionnaire voit aussi les enregistrements propagés (`uvicorn.asgi` remonte au gestionnaire `default` du logger `uvicorn`). Il agit sur trois familles, reconnues par la forme du message et la position des arguments, jamais d'après la forme de la valeur (checklist §1) :
  1. **En-têtes, ligne de requête et trames de websockets (DEBUG)** : `"< %s %s %s"`, `"< %s: %s"`, `"> %s: %s"`, et les trames `"< %s"` et `"> %s"` (un seul argument, l'objet `Frame`). Leurs arguments deviennent `<masqué>`. Cela couvre le ticket, `Authorization` d'un client non navigateur et le curseur, celui de la requête comme celui du `hello`. Restent lisibles `"> HTTP/1.1 %d %s"` (statut) et `"> [body] (%d bytes)"` (longueur seule). Écartée : restreindre l'assertion du test à la ligne de requête, qui laisserait le curseur et les références des trames dans les journaux DEBUG.
  2. **Refus de poignée de main de websockets (DEBUG et ERROR)** : tout message qui commence par `"! "` (`"! invalid handshake"`, `"! invalid origin"`, `"! header fields too large"`, `"! no valid HTTP request"`…) et `"opening handshake failed"`. Le filtre met `exc_info`, `exc_text` et `stack_info` à `None` et ajoute « (détail masqué) » au message. La trace porte le message de l'exception, qui recopie l'en-tête reçu (§0). Le filtre ne garde pas `exc_info` en se contentant de masquer les arguments, car le formateur réécrirait la trace.
  3. **Scope d'uvicorn (TRACE)** : sur `uvicorn.asgi`, l'argument de `"%s [%d] Started scope=%s"` devient `<scope masqué>`. Dans `"… Receive %s"` et `"… Send %s"`, chaque message ASGI est réduit à sa clé `type`. Cela couvre `subprotocols` (le ticket) et `query_string` (le curseur), que `message_with_placeholders` laisse passer.
- `nexus` et `nexus-dev` ne passent aucun `log_level` : TRACE n'est atteint que par une configuration faite exprès. Le filtre le couvre quand même, car un `uvicorn_log_config()` modifié ou un `Config(log_level="trace")` suffit à installer `MessageLoggerMiddleware`, et le test le prouve.
- **Écho du refus 400 de websockets.** Quand `ServerProtocol.accept` refuse lui-même la poignée de main (en-tête mal formé, §0), le corps du 400 recopie le message de l'exception, donc l'en-tête reçu et le ticket (`websockets/server.py:200-207`), à tout niveau de journal. C'est une **exception à ADR-006** (« aucun token … n'est … transmis », `DECISIONS.md:52`) et à la checklist §1 qui l'applique (« Nothing received is echoed back in a response »), **acceptée par Loïc le 2026-10-13** (§2, décision 2). Raisons :
  - l'écho ne va qu'à l'expéditeur, sur sa propre connexion, et il détient déjà le ticket ;
  - un navigateur ne peut pas produire cet en-tête (`new WebSocket` lève `SyntaxError` sur un nom de sous-protocole invalide), ni le client websockets : `websockets.connect(subprotocols=…)` valide chaque nom (`websockets/asyncio/client.py:300-301`) et lève `ValueError` sur une espace (`websockets/headers.py:480-482`, vérifié) ; seul un client écrit à la main, ou la couche sans E/S `ClientProtocol`, qui ne valide pas, peut l'envoyer ;
  - le ticket est à usage unique et vit 30 s au plus ; ce refus ne le consomme pas, mais l'expéditeur qui le réessaie correctement le brûle, et sinon il périme.

  Seul un intermédiaire qui journaliserait les corps de réponse le verrait : Vite ne le fait pas, et `tailscale serve` est déconseillé. L'exception est écrite à trois endroits : une ligne sous ADR-006 dans `DECISIONS.md`, ajoutée par la PR A, qui fait exister le ticket (texte proposé : « Exception (2026-10-13, #57) : le corps du refus 400 que websockets renvoie à une poignée de main mal formée recopie l'en-tête `Sec-WebSocket-Protocol`, ticket WebSocket compris, vers son seul expéditeur ; accepté, voir `docs/superpowers/specs/2026-10-08-ws-ticket-design.md` §3.6 ») ; SECURITY §3 ; le corps de la PR A. Parce qu'elle touche `DECISIONS.md`, la PR A ne se fusionne que sur un « fusionne » explicite de Loïc (§6). La ligne ne cite pas ADR-021, qui n'existe qu'avec la PR B (§5) ; la PR B pourra y ajouter le renvoi. **Pas de parade de code.** Écartée : une sous-classe de `WebSocketsSansIOProtocol` passée par `Config(ws=…)` qui viderait le corps de tout refus. Elle surchargerait `handle_connect`, une méthode interne d'uvicorn de plus (§7), pour un écho vers l'expéditeur seul. Le test des journaux (§4) constate l'écho, pour que la note soit revue si websockets cesse de recopier l'en-tête.
- Rien d'autre ne lit le ticket : il n'entre ni dans un 4xx de Nexus, ni dans `hello`, ni dans la base.

### 3.7 `NEXUS_HOST` et `Host` (PR B)

- `config.py` : `host` devient `hosts: tuple[str, ...]`.
  - **Lecture.** `from_env` découpe `NEXUS_HOST` sur les virgules et retire les espaces autour de chaque entrée, comme pour `NEXUS_ALLOWED_HOSTS`. Une entrée vide est refusée. Comme `from_env` retire aussi `\n`, le refus de `100.64.0.1\n` se teste au niveau de `Settings(hosts=…)` : la validation de `__post_init__` porte sur la valeur telle que reçue, sans nettoyage.
  - **Validation (D9).** Par `ipaddress`, en forme normalisée, avec `scope_id` refusé explicitement. Le message d'erreur ne recopie rien.
  - **Boucle locale.** Au plus **une entrée** de boucle locale, plus au plus une adresse du tailnet ; `127.0.0.1,::1` est refusé, comme deux adresses du tailnet. Chaque entrée de boucle locale donne des sockets par une table fixe, sans `getaddrinfo` (un fichier `hosts` ne choisit pas l'adresse d'écoute) :
    - `127.0.0.1` → une socket IPv4 ;
    - `::1` → une socket IPv6 ;
    - `localhost` → `127.0.0.1` et `::1`, comme `uvicorn.run(host="localhost")` aujourd'hui (§0). `localhost` se réduit à `127.0.0.1`, avec un message de niveau DEBUG, dans deux cas seulement, qui disent qu'IPv6 manque sur la machine : `EAFNOSUPPORT` à la création de la socket `AF_INET6` (noyau sans IPv6), et `EADDRNOTAVAIL` au bind de `::1` (IPv6 désactivé sur la boucle locale). **Toute autre `OSError` est fatale, `EADDRINUSE` compris** : si un autre processus tient `[::1]:port`, un client qui résout `localhost` en `::1` lui parlerait et lui enverrait son jeton porteur. Le même risque existe en service, quand une écoute de boucle locale perdue ne peut pas être reprise parce qu'un autre processus a pris le port : Nexus ne peut plus refuser de démarrer, il l'écrit en WARNING (« Journal par changement d'état », plus bas, et §7). Le code est lu dans `exc.errno` et comparé aux constantes du module `errno`, jamais au message ; sous Windows, `errno` y range les codes `WSAE…` que lèvent les sockets.
  - **Entrée ajoutée d'office.** Sans entrée de boucle locale, `127.0.0.1` est ajouté : c'est la cible du proxy Vite et la valeur par défaut de `NEXUS_HOST`.
  - **Échec de bind au démarrage.** Un échec sur une adresse de boucle locale est fatal, comme aujourd'hui (sortie : voir « Lancement »). Les seules exceptions sont les deux cas de repli de `localhost` ci-dessus. L'adresse du tailnet n'est jamais liée par `serve` : son premier bind a lieu dans la tâche de surveillance, juste après le démarrage, et ses échecs suivent les règles de la reprise ; en service, toute écoute perdue est reprise, boucle locale comprise (décision de Loïc du 2026-10-13, « La tâche de surveillance », plus bas).
  - **Messages.** Aucun message de Nexus sur un bind de l'adresse du tailnet ne recopie `str(exc)` ni `exc_info` : `socket.create_server` ajoute l'adresse au message de l'erreur (« while attempting to bind on address », `socket.py:951-953`). Seuls le type de l'exception et `errno` sont écrits. La même règle vaut pour le contrôle auprès de Tailscale : ni sa sortie (état, adresses et nom du nœud, nom du tailnet), ni son erreur, ni `str(exc)` ne sont écrits.
- **Contrôle de l'adresse auprès de Tailscale (décision de Loïc du 2026-10-13, D9).** Avant chaque bind de l'adresse du tailnet, au premier tour de la tâche de surveillance, juste après le démarrage, comme à chaque reprise, Nexus vérifie que Tailscale est connecté et que cette adresse fait partie des adresses qu'il a données à ce nœud. Tant que l'écoute du tailnet est servie, la tâche refait ce contrôle à chaque tour. La boucle locale n'est jamais contrôlée.
  - **Mécanisme.** `nodes.py` gagne `run_tailscale_self(binary) -> str`, sœur de `run_tailscale` : `[binary, "status", "--json", "--peers=false"]`, mêmes options (`capture_output`, `encoding="utf-8"`, `check=True`, `CREATE_NO_WINDOW` sous Windows) et même borne `timeout=TIMEOUT_SECONDS` (5 s), que `subprocess.run` applique en tuant le processus enfant. `--peers=false` fait passer la CLI par `StatusWithoutPeers` (`cmd/tailscale/cli/status.go`, `runStatus`) : même statut, sans la liste des pairs. `serve` reçoit ce runner par injection (`tailnet_status: nodes.Runner`, par défaut `partial(nodes.run_tailscale_self, settings.tailscale_bin)`), comme `create_app` reçoit `nodes_runner` : les tests passent un runner factice, jamais le vrai binaire. Si la CLI de Helios refuse `--peers=false`, le repli est `[binary, "status", "--json"]`, même lecture et même borne de 5 s (§2, contrôles).
  - **Pourquoi pas `tailscale ip`, prévu d'abord.** Commande précisée après la quatrième relecture, car `tailscale ip` garde l'adresse de la netmap quand Tailscale est arrêté. Vérifié sur la branche `main` de Tailscale : `runIP` (`cmd/tailscale/cli/ip.go`) imprime `st.TailscaleIPs` sans regarder `BackendState`, et `updateStatusLocked` (`ipn/ipnlocal/local.go`) remplit ce champ depuis la netmap. `tailscale down` (état `Stopped`) et l'expiration de la clé (état `NeedsLogin`) gardent la netmap (`nextStateLocked`) mais retirent l'adresse de l'interface (`enterStateLocked` reconfigure le moteur à vide, `router.Config{}`) : `tailscale ip` sort alors avec 0 et rend encore l'adresse. Seule une déconnexion du compte (`logout`, `resetForProfileChangeLocked`) vide la netmap. Écarté aussi : `tailscale status --json` complet (celui de `nodes`), même lecture mais avec tous les pairs à chaque tour ; il ne reste que comme repli.
  - **Jamais sur la boucle d'événements.** L'appel passe par `asyncio.wait_for(asyncio.to_thread(runner), timeout=check_timeout)`, où `check_timeout` est injectable (6 s par défaut, réduit par les tests, §4). `wait_for` rend la main à la tâche au bout du délai, mais n'arrête pas le thread : une fonction synchrone déjà lancée par `to_thread` ne s'annule pas. La borne de 5 s vient de `subprocess.run(timeout=5)`, qui tue le processus enfant : elle ne vaut que pour le runner par défaut. D'où deux règles :
    - **contrat du point d'injection** : un runner injecté doit rendre la main de lui-même en un temps borné ; `wait_for` protège la tâche, pas le thread ;
    - **tests** : un test qui bloque un runner le libère avant de finir. Sinon l'arrêt attend ce thread : `asyncio.run` attend l'exécuteur par défaut jusqu'à 300 s sous `asyncio` de Python 3.13 (`asyncio/runners.py:73-74`, `THREAD_JOIN_TIMEOUT`), puis la sortie de l'interpréteur attend encore ses threads (`concurrent/futures/thread.py:23-37`) ; sous uvloop, l'attente n'a aucune borne (`loop.pyx:3237-3240`).

    Le contrôle ne retarde jamais la mise en service : les sockets de boucle locale sont servies avant le premier tour de la tâche. À l'arrêt par `should_exit` ou par SIGINT, un contrôle en cours retarde la fin du processus de 5 s au plus avec le runner par défaut, car `asyncio.run` attend les threads de son exécuteur par défaut (`Runner.close`). Pas sous SIGTERM : uvicorn relance le signal avec le gestionnaire par défaut à la fin de `serve` (`server.py:343-349`), le processus meurt avant `Runner.close`, et un processus `tailscale` encore en cours peut survivre à Nexus, orphelin, jusqu'à ce qu'il finisse de lui-même.
  - **Lecture de la sortie.** La sortie est lue par `json.loads` ; elle doit être un objet. Tailscale est connecté si `BackendState` vaut exactement `"Running"`, la même règle que `nodes._read` ; tout autre état (`Stopped`, `NeedsLogin`, `NeedsMachineAuth`, `Starting`, `NoState`) rend la réponse non confirmée, même si la sortie porte encore des adresses. Les adresses du nœud sont dans le champ `TailscaleIPs` du statut (`ipn/ipnstate/ipnstate.go`, `Status.TailscaleIPs`, celui que lit `tailscale ip`) ; `Self.TailscaleIPs` vient de la même netmap et n'est pas lu. Ce champ doit être une liste de chaînes (absent ou `null` : aucune adresse) ; chaque entrée est lue par `ipaddress.ip_address`, et une entrée qui n'est pas une adresse rend la réponse « inattendue », donc non confirmée. L'adresse configurée, déjà en forme normalisée (D9), est confirmée si elle est égale à l'une d'elles. La comparaison porte sur des objets `ipaddress`, jamais sur du texte : `fd7a:115c:a1e0:0:0:0:0:1` et `fd7a:115c:a1e0::1` sont la même adresse.
  - **Issue.** Confirmée : le bind est tenté (et ses échecs suivent les règles du bind). Non confirmée, pour quelque raison que ce soit : pas de bind, l'écoute est « en attente », nouvel essai au tour suivant (30 s). Sur une écoute servie, une adresse qui n'est plus confirmée ferme l'écoute comme une écoute perdue (étape 2 bis plus bas). Le contrôle échoue fermé : aucune issue incertaine n'ouvre le port.
  - **Exceptions du runner.** Le contrôle attrape exprès **toute** `Exception` du runner et de la lecture, pas seulement les cas prévus ci-dessous : une exception imprévue vaut « non confirmée », raison « contrôle de Tailscale en échec », avec le seul type de l'exception. C'est un écart délibéré à la règle de la checklist sur les exceptions étroites (« Error suppression is as narrow as the expected case », `docs/agents/review-checklist.md`), pour deux raisons : le contrôle doit échouer fermé quoi que fasse un runner injecté ou une CLI d'une autre version, et une exception qui remonterait arrêterait la surveillance de toutes les écoutes, boucle locale comprise. Le bogue reste visible, comme le veut la règle : son type est écrit en WARNING au changement d'état. `BaseException` (`CancelledError` comprise) n'est pas attrapée.
  - **Cas limites.** Chaque raison est faite de mots fixes ; jamais la sortie de Tailscale, ni l'état qu'elle donne, ni `str(exc)`.
    - CLI `tailscale` absente (`FileNotFoundError`, ou `OSError` sur un chemin invalide de `NEXUS_TAILSCALE_BIN`) : non confirmée, raison « Tailscale introuvable ». L'écoute du tailnet n'ouvre jamais tant que la CLI manque ; la boucle locale sert normalement.
    - Tailscale arrêté (`tailscale down`, état `Stopped`), clé expirée (`NeedsLogin`) ou pas encore connecté : la commande sort avec 0 et la sortie garde souvent les adresses du nœud. Non confirmée, raison « Tailscale pas connecté ».
    - Démon `tailscaled` injoignable, ou option refusée par une CLI ancienne : la commande sort avec un code non nul (`CalledProcessError`). Non confirmée, raison « lecture de Tailscale impossible ».
    - Sortie qui n'est pas du JSON, ou de forme inattendue : non confirmée, raison « réponse de Tailscale inattendue ».
    - État `Running` sans l'adresse configurée : non confirmée, raison « adresse absente de Tailscale ».
    - Délai dépassé (`subprocess.TimeoutExpired` ou `TimeoutError` de `wait_for`) : non confirmée, raison « Tailscale ne répond pas ».
    - Adresse changée pendant que l'écoute est servie (nouvelle adresse donnée par Tailscale, nœud réenregistré) : le contrôle du tour suivant ne la trouve plus ; l'écoute est fermée et passe « en attente ». Fenêtre : environ 30 s en pratique, car un contrôle dure bien moins d'une seconde ; **42 s au plus** (30 + 6 + 6) : le contrôle qui a confirmé l'adresse peut avoir lu l'état de Tailscale au début de sa borne de 6 s, la tâche attend ensuite l'intervalle de 30 s, et le contrôle suivant peut prendre jusqu'à 6 s avant de rendre « non confirmée ». Une adresse configurée qui n'est plus celle de Tailscale reste en attente jusqu'à ce que Loïc corrige `NEXUS_HOST` : Nexus ne suit pas une nouvelle adresse tout seul.
    - Adresse IPv6 de Tailscale (`fd7a:115c:a1e0::/48`) : `TailscaleIPs` porte l'IPv4 et l'IPv6 du nœud, et la comparaison sur objets `ipaddress` couvre les deux formes d'écriture. Une adresse configurée en IPv6 n'est confirmée que si Tailscale la donne ; IPv6 désactivé côté Tailscale vaut « absente ».
  - **Ce que le contrôle ne prouve pas.** Il fait confiance au binaire `tailscale` local et au démon `tailscaled` : un binaire remplacé ou un `NEXUS_TAILSCALE_BIN` qui vise autre chose répond ce qu'il veut. C'est la limite assumée d'ADR-020 D5 (un agent local décidé à tricher). Il dit que l'adresse appartient à Tailscale au moment du contrôle, pas jusqu'au contrôle suivant (fenêtre de 42 s au plus, « Cas limites » ci-dessus). Surtout, il ne dit rien de l'interface par laquelle arrivent les paquets : le modèle d'hôte faible (§1) reste entier. Il réduit donc le besoin de la règle de pare-feu par interface sans la remplacer, et cette règle reste une **recommandation**, non imposée par le code (décision du 2026-10-13).
- **Lancement, fichier nouveau `nexus/serving.py`.** Une seule `uvicorn.Config` et un seul `uvicorn.Server`, sous une coroutine qui appartient à Nexus. Vérifié sur uvicorn 0.54.0, uvloop 0.22.1 et `asyncio` de Python 3.13 :
  - `main()` construit `config = uvicorn.Config(create_app(settings), access_log=False, log_config=uvicorn_log_config())`, puis appelle `asyncio.run(serve(config, settings), loop_factory=config.get_loop_factory())`. C'est ce que fait `Server.run` (`server.py:86`), mais `Server.run` possède sa boucle et n'accepte rien à côté de `serve`. `get_loop_factory()` garde uvloop là où il est installé (Linux) et la boucle par défaut d'`asyncio` ailleurs (Windows, Helios).
  - `serve` ouvre les sockets de boucle locale (`socket.create_server((adresse, port), family=AF_INET ou AF_INET6, backlog=config.backlog)`). Il ne contrôle ni ne lie l'adresse du tailnet : il la passe à la tâche de surveillance à l'état « en attente, premier contrôle », qui n'est pas un état d'échec, et les écoutes de boucle locale à l'état « servie ». Le premier contrôle et le premier bind du tailnet ont donc lieu au premier tour de la tâche, juste après le démarrage (plus bas), et Tailscale ne retarde jamais la boucle locale. Un échec fatal sur la boucle locale ferme les sockets déjà ouvertes (`try/finally`) et remonte à `main()`. `serve` construit ensuite `NexusServer(config, écoutes, tailnet_status=…, check_timeout=…, interval=…, between_rounds=…)`, appelle `await server.serve(sockets=…)` avec les seules sockets de boucle locale et rend `server.started`. `serve` n'écrit rien avant `await server.serve()`.
  - Avec `sockets`, uvicorn n'écrit pas « Uvicorn running on … » (`server.py:198-203`) : `NexusServer.startup` écrit sa propre ligne de démarrage en INFO (plus bas), là où uvicorn écrit la sienne, après un démarrage réussi. Un lifespan en échec (`sys.exit(STARTUP_FAILURE)` dans `Server.startup`, `server.py:116-118`) n'annonce donc rien, et surtout pas un contrôle du tailnet qui n'aura jamais lieu.
  - **`main()` garde l'enveloppe de `uvicorn.run`** (`uvicorn/main.py:622-640`) : `except KeyboardInterrupt: pass` autour d'`asyncio.run`, car uvicorn relance SIGINT après l'arrêt (sortie 0, sans trace). Un échec de bind de la boucle locale, levé par `serve` avant le lifespan, est écrit sur `uvicorn.error` comme le fait `Server.startup` aujourd'hui (`logger.error(exc)`, `server.py:189-192`, adresse de boucle locale comprise), puis `main()` sort avec le code **3** (`STARTUP_FAILURE`). Comme `uvicorn.run`, `main()` sort aussi avec 3 quand `serve` rend `started` faux. Un échec du lifespan sort déjà avec 3 depuis `Server.startup`.
- **`NexusServer(uvicorn.Server)` surcharge deux méthodes publiques.**
  - `startup(sockets)` appelle `super().startup(sockets)`, puis ne fait rien d'autre si `self.started` est faux (`Server.startup` le met à vrai en dernier, `server.py:205`). Si `self.started` est vrai et que `self.should_exit` est faux, elle crée la tâche de surveillance des écoutes. `servers`, `server_state` et `lifespan` n'existent qu'à ce moment-là. Si `self.started` est vrai, elle écrit ensuite la ligne de démarrage sur `nexus`, en mots fixes et sans l'adresse du tailnet : le port, le nombre d'écoutes de boucle locale et, si une adresse du tailnet est configurée et que la tâche vient d'être créée, « tailnet : contrôle auprès de Tailscale à venir ». C'est la seule ligne de démarrage qui parle du tailnet, en INFO ; l'issue du premier contrôle s'écrit au premier tour de la tâche (« Journal par changement d'état », plus bas).
  - `shutdown(sockets)` **annule d'abord** la tâche de surveillance et l'attend par `await asyncio.wait({tâche})`, qui ne relève ni l'annulation ni l'exception de la tâche. Le tout est dans un `try`, et `super().shutdown(sockets)` dans son `finally` : l'arrêt d'uvicorn a toujours lieu, même si la tâche est déjà morte d'une erreur ou si l'attente lève.
- **La tâche de surveillance** garde, pour chaque écoute (boucle locale et tailnet), l'adresse, la famille, l'état reçu de `serve` puis tenu à jour (« Journal par changement d'état », plus bas), la socket passée à uvicorn et son `asyncio.Server`, ou rien si l'écoute est en attente. Elle boucle tant que `should_exit` est faux. **À chaque tour, elle traite d'abord les écoutes de boucle locale (étapes 2 à 6), puis celle du tailnet (étapes 2, 2 bis, puis 3 à 6)** : le contrôle auprès de Tailscale ne retarde jamais la reprise de la boucle locale. **Le runner est appelé une fois par tour au plus**, à l'étape 2 bis ou à l'étape 3, jamais aux deux : le contrôle ne prend donc pas plus de 6 s d'un tour.
  1. Elle attend l'intervalle (30 s, injectable), sauf avant le premier tour, qui a lieu dès sa création : c'est là que l'écoute du tailnet, « en attente, premier contrôle », est contrôlée et liée pour la première fois. L'attente passe par une coroutine injectable (`between_rounds`, par défaut `asyncio.sleep(interval)`) : un test peut la remplacer par une attente sur un `asyncio.Event` qui lui signale aussi chaque fin de tour, et compter les appels d'un tour sans dépendre d'une durée (§4).
  2. **Écoute perdue.** Pour chaque écoute servie dont la socket a `fileno() == -1` (test fait par une petite fonction du module, que les tests peuvent remplacer, §4), elle écrit un avertissement sur `nexus`, sans l'adresse (« écoute perdue sur le tailnet » ou « sur la boucle locale », reprise toutes les 30 s), appelle `server.close()` dans un `try` (le serveur est déjà mort), le retire de `self.servers`, et l'écoute repasse « en attente » avec la raison « perdue ». Les connexions déjà acceptées par cette écoute restent dans `server_state.connections` et continuent. Le test porte sur la socket, pas sur le serveur, car `Server.is_serving()` reste vrai dans les deux cas suivants :
     - sous la boucle proactor de Windows (Helios), la boucle d'acceptation ferme la socket d'écoute pour de bon à la première `OSError` d'`AcceptEx` (`asyncio/proactor_events.py:862-869`), par exemple un client qui réinitialise sa connexion avant l'acceptation (WinError 64) ou l'adresse `100.x` retirée par un redémarrage de Tailscale ;
     - sous uvloop, une erreur du rappel d'écoute ferme le serveur (`uvloop/handles/streamserver.pyx:137-144`, puis `_fatal_error`), sans rien journaliser quand c'est une `OSError`, et détache la socket.
  2 bis. **Adresse du tailnet plus confirmée.** Si l'écoute du tailnet est servie, elle refait le contrôle auprès de Tailscale. Non confirmée : avertissement sur `nexus`, sans l'adresse, avec la raison du contrôle en mots fixes (« écoute du tailnet fermée : adresse non confirmée par Tailscale (Tailscale pas connecté) », par exemple ; jamais la sortie du runner), puis même traitement qu'une écoute perdue : `server.close()`, retrait de `self.servers`, passage « en attente » avec la raison du contrôle. Les connexions déjà acceptées continuent : elles sont arrivées pendant que l'adresse était celle de Tailscale, et chaque tour de lecture revérifie leur jeton (D6). **Une écoute fermée ici saute l'étape 3 à ce tour** : elle vient d'être contrôlée, et un second appel du runner au même tour doublerait la durée du tour (12 s) pour une réponse vieille de quelques secondes. Elle est contrôlée de nouveau, puis liée si l'adresse est confirmée, au tour suivant. À l'inverse, une écoute du tailnet perdue à l'étape 2 n'est plus servie : l'étape 2 bis ne la contrôle pas, et l'étape 3 la contrôle et la relie au même tour, avec un seul appel du runner.
  3. **Écoute en attente.** Pour chaque écoute en attente, sauf l'écoute du tailnet fermée à l'étape 2 bis de ce tour, elle tente le bind, précédé du contrôle auprès de Tailscale pour l'adresse du tailnet. Juste avant chaque bind, donc après le retour du contrôle pour l'adresse du tailnet, et sans `await` entre ce test et le bind (`socket.create_server` est synchrone), elle teste `self.should_exit` : s'il est vrai, elle s'arrête sans lier. Un échec est journalisé selon la règle ci-dessous (type et `errno` seulement).
  4. Si le bind réussit, elle appelle `server = await loop.create_server(lambda: config.http_protocol_class(config=config, server_state=self.server_state, app_state=self.lifespan.state), sock=s, backlog=config.backlog, start_serving=False)`. Cette fabrique est celle de `Server.startup` (`server.py:122-130`) ; `ssl` n'est pas utilisé. Avec `sock=`, rien ne garantit que la socket soit fermée si `create_server` lève : la tâche la ferme elle-même. **Seule une `OSError` est absorbée** : elle ferme `s`, s'écrit pour cette écoute selon la règle ci-dessous (raison « mise en service en échec », avec le type et `errno`), laisse l'écoute « en attente », et la tâche continue : nouvel essai au tour suivant, les autres écoutes du tour étant traitées normalement. Toute autre exception ferme `s` et est relevée : une `Exception` va à l'étape 7, une `BaseException` (`CancelledError` comprise) remonte hors de la tâche. Étroite ici, contrairement au contrôle auprès de Tailscale, car le code appelé est celui de la boucle et non un point d'injection, et ses échecs attendus sont des `OSError` du système (`sock.setblocking` sous `asyncio`, `TCPServer._open` sous uvloop, `loop.pyx:1833-1845`) ; une autre exception (`ValueError` sur le type de socket, `RuntimeError` interne d'uvloop) est un bogue, qu'il ne sert à rien de retenter toutes les 30 s et que l'étape 7 écrit en ERROR (checklist, « Error suppression is as narrow as the expected case »).
  5. **Sans `await` entre les deux**, elle teste `self.should_exit` : s'il est vrai, elle ferme le serveur et s'arrête ; sinon, elle fait `self.servers.append(server)`.
  6. Elle appelle ensuite `await server.start_serving()`, écrit « écoute … reprise » une fois par reprise, sans l'adresse, et **continue de surveiller**. Même règle qu'à l'étape 4 : une `OSError` de `start_serving` (`sock.listen` sous `asyncio`, `base_events.py:317` ; `uv_listen` sous uvloop, `handles/streamserver.pyx:58-63`) ferme le serveur (`server.close()` dans un `try`), le retire de `self.servers` sans `await` entre les deux, et laisse l'écoute « en attente » avec la raison « mise en service en échec » ; toute autre `Exception` va à l'étape 7, le serveur étant déjà dans `servers` ; `CancelledError` remonte, et `shutdown` ferme le serveur.
  7. Le corps de la tâche est enveloppé d'un `except Exception` qui **ferme d'abord l'écoute du tailnet** (échec fermé) si elle est servie ou en cours de reprise (bind réussi à ce tour, pas encore servie) : `server.close()` dans un `try` et retrait de `self.servers` si son serveur y est, et fermeture de sa socket si elle est liée sans être encore servie (par sûreté : les étapes 4 et 6 la ferment déjà). Une écoute du tailnet qui n'est plus contrôlée n'est plus servie : sans cela, une adresse qui cesse d'être celle de Tailscale resterait écoutée sans limite. Les connexions déjà acceptées continuent, comme à l'étape 2 bis. Le gestionnaire écrit ensuite une ligne ERROR sur `nexus`, en mots fixes, avec le seul type de l'exception, sans message ni `exc_info` (ils peuvent porter l'adresse), puis rend la main. La ligne dit ce qui vient d'être fait, et rien de plus :
     - « surveillance des écoutes arrêtée : écoute du tailnet fermée », si l'écoute du tailnet était servie ou en cours de reprise ;
     - « surveillance des écoutes arrêtée », sans un mot du tailnet, si aucune adresse du tailnet n'est configurée ou si son écoute était en attente (premier contrôle compris) : rien n'était ouvert, et rien ne l'ouvrira jusqu'au redémarrage.

     Les écoutes de boucle locale continuent de servir, sans surveillance jusqu'au redémarrage. `CancelledError` n'est pas absorbée : la tâche écrit une ligne DEBUG (« surveillance des écoutes annulée ») et la relève ; c'est `shutdown` qui ferme alors toutes les écoutes. `shutdown` reste sûr grâce à son `finally`.

  La reprise d'une écoute de **boucle locale** perdue en service est **décidée par Loïc le 2026-10-13** (D10) : le même défaut de la boucle proactor frappe déjà `uvicorn.run` aujourd'hui sur Helios, et le mécanisme est le même, sans contrôle Tailscale. Au démarrage, un échec de bind de la boucle locale reste fatal.

  **Journal par changement d'état.** Chaque écoute a un état : « servie », « en attente, premier contrôle » (tailnet seulement, état initial reçu de `serve`, qui n'est pas un échec), ou « en attente » avec sa raison d'échec (perdue ; non confirmée, avec la raison du contrôle ; échec de bind, avec son `errno` ; mise en service en échec, avec le type de l'exception et son `errno`). L'état vit dans la tâche dès sa création : ni `serve` ni `NexusServer.startup` n'écrivent de WARNING sur le tailnet (la ligne de démarrage dit seulement, en INFO, « contrôle auprès de Tailscale à venir »), et le premier échec, quel qu'il soit, s'écrit une seule fois, au premier tour. Entrer dans un état d'échec, ou passer d'une raison d'échec à une autre, s'écrit **une fois** en WARNING sur `nexus`, sans l'adresse ; le même échec répété aux tours suivants s'écrit en DEBUG ; le retour à « servie » s'écrit une fois (« écoute … reprise » ; au premier bind du tailnet, « écoute du tailnet ouverte »). Une perte suivie, au même tour, d'un échec de reprise donne donc deux WARNING : la perte, puis la raison de l'échec. Une fermeture à l'étape 2 bis n'en donne qu'un à son tour, puisque l'étape 3 n'a pas lieu ; si le tour suivant trouve la même raison, elle s'écrit en DEBUG. Une reprise qui échoue sans fin laisse une trace visible au niveau par défaut, sans une ligne toutes les 30 s.
  - **`EADDRINUSE` sur une reprise** a son propre message, car il dit qu'un autre processus tient le port : sur la boucle locale, « port de la boucle locale pris par un autre processus : les clients locaux (proxy Vite) peuvent lui envoyer leur jeton ». C'est le cas que le démarrage refuse pour `::1` (plus haut). Scénario : sous la boucle proactor de Windows, l'écoute `127.0.0.1` meurt (WinError 64), un autre processus local prend `127.0.0.1:8765`, et le proxy Vite lui envoie le jeton porteur de Loïc. Nexus ne peut que le signaler (§7).
  - **Reprise sous Windows non vérifiée.** `socket.create_server` ne pose pas `SO_REUSEADDR` sous Windows (`socket.py:921-937`). Les connexions acceptées par l'écoute morte restent ouvertes, dont la WebSocket longue du proxy Vite, et rien ne garantit qu'un nouveau bind du même port réussisse tant qu'elles existent. Si ce bind échoue, l'échec suit la règle ci-dessus (WARNING une fois, avec son `errno`), et l'écoute reste en attente jusqu'à la fermeture de ces connexions. À vérifier sur Helios (§2, contrôles) ; si le bind échoue, une suite possible est de fermer les connexions de l'écoute morte, ce que cette conception ne prévoit pas.

  Pourquoi c'est sûr :
  - `create_server(sock=…, start_serving=False)` ne suspend jamais. Dans `asyncio.base_events`, les seuls `await` sont la résolution d'un `host` (absent ici) et le `sleep(0)` qui suit `_start_serving` quand `start_serving` est vrai (`base_events.py:1665-1668`). uvloop n'a pas de `sleep(0)` : son `create_server` ne suspend que pour résoudre un `host`, et il appelle `_start_serving` sans attendre (`loop.pyx:1851-1852`). L'annulation ne peut donc pas tomber entre le bind et l'ajout.
  - `start_serving` ne suspend pas sous uvloop (`server.pyx:100-101`) ; sous `asyncio`, elle suspend une fois (`sleep(0)`, `base_events.py:362-366`). Une annulation à ce moment trouve le serveur déjà dans `servers`, et `shutdown` le ferme.
  - Le contrôle auprès de Tailscale suspend (`to_thread`), mais toujours **avant** le bind (étape 3) ou avant la fermeture (étape 2 bis) : aucune socket n'est ouverte par la tâche pendant cette attente, et une annulation à ce moment ne laisse rien à fermer. Un `should_exit` mis pendant cette attente, sans annulation encore (`main_loop` le voit dans les 0,1 s, `server.py:242-249`), est vu par le test de l'étape 3 avant le bind.
  - Seule la tâche modifie `self.servers` pendant le service, sans `await` entre le test et la modification ; `shutdown` l'annule et l'attend avant de parcourir `servers`.
  - `shutdown` ne s'exécute qu'après `main_loop`, qui ne rend la main que quand `should_exit` est vrai (`server.py:106-109`). Elle ferme tout `self.servers` (l'`asyncio.Server` ferme ses sockets d'écoute), et les connexions de la nouvelle écoute sont dans le même `server_state.connections`. Elles reçoivent donc `shutdown()` (1012 pour un WebSocket) et sont attendues comme les autres.
- **Protocole servi.** `config.http_protocol_class` est résolu une fois par `Config.load()` : `HttpToolsProtocol` avec `http="auto"`, car httptools est installé (`protocols/http/auto.py`). Il passe au WebSocket par `config.ws_protocol_class`, `WebSocketsSansIOProtocol` avec `ws="auto"` (`protocols/websockets/auto.py`). Les deux écoutes servent la même application enveloppée (`config.loaded_app`), avec le même lifespan, `app.state` (tickets, `live_instance`) et en-têtes par défaut.
- **Pourquoi pas un second `uvicorn.Server`.** Une seconde `Config` relance `configure_logging()` (`config.py:303`). Avec sa valeur par défaut (`log_config=LOGGING_CONFIG`, `config.py:214`), le `dictConfig` recrée les gestionnaires sans `WebSocketPathFilter` ni le nouveau filtre et rend sa sortie à `uvicorn.access`. Même avec `uvicorn_log_config()`, il recréerait les gestionnaires en plein service. Chaque `serve()` installe aussi ses gestionnaires de signaux (`capture_signals`, `signal.signal`) : le dernier lancé capture SIGTERM. Enfin, les deux arrêts se feraient sans ordre. Ici, il n'y a qu'une configuration de journaux et qu'un propriétaire des signaux. uvicorn relance le signal capturé après l'arrêt (`server.py:348-349`) : le processus finit par SIGTERM, comme `uvicorn.run` aujourd'hui.
- **Dépendance.** Ce montage s'appuie sur des attributs non documentés d'uvicorn (`servers`, `server_state`, `lifespan`, la signature de `http_protocol_class`) et sur un comportement non documenté des boucles (une écoute morte laisse sa socket à `fileno() == -1`). Les tests de vrai serveur (§4) sont le garde-fou, à relancer à chaque montée de version d'uvicorn (§7).
- `dev()` garde `uvicorn.run(reload=True)` sur une seule valeur et refuse une adresse non loopback avec un message clair.
- `app.py` : `HostCheckMiddleware(allowed_hosts=settings.allowed_hosts | adresses littérales de NEXUS_HOST)` (D11).

  - **Échecs répétés de reprise** : une écoute de boucle locale perdue, puis un bind injecté qui lève `EADDRINUSE` trois tours de suite, le premier au tour de la perte : **deux** WARNING au premier tour, la perte puis l'échec avec le message propre à `EADDRINUSE` (port pris par un autre processus), puis DEBUG aux deux tours suivants ; puis `EADDRNOTAVAIL` : un WARNING de plus ; puis succès : une ligne de reprise. Même chose sur l'écoute du tailnet, avec le message générique.
  - **Échec de la mise en service** (injecté) après un bind réussi : une `OSError` levée par `create_server` ferme la socket (le port est libre), laisse `servers` inchangé, donne un WARNING pour cette écoute avec le type et `errno` (raison « mise en service en échec »), puis DEBUG si elle se répète ; la tâche continue, les autres écoutes du tour sont traitées, et le tour suivant, sans l'erreur injectée, rouvre l'écoute. Même chose pour une `OSError` levée par `start_serving` : le serveur est fermé et quitte `servers`, le port est libre. Tests unitaires de l'étape 4 : une `RuntimeError` injectée dans `create_server` ferme aussi la socket et remonte hors de l'étape 4 (elle n'est pas absorbée, et c'est l'étape 7 qui la reçoit) ; une `CancelledError` au même endroit ferme la socket et remonte, sans WARNING.
  - **Arrêt pendant la reprise** : `should_exit` est mis entre le bind et l'ajout (bind injecté qui lève le drapeau). Le serveur créé est fermé, `servers` est inchangé, et le port est libre après l'arrêt.
  - **Tâche morte** : la panne est une `RuntimeError` levée par la fonction de l'étape 2 qui teste la socket d'une écoute servie (remplacée par le test, §3.7). Le contrôle auprès de Tailscale absorbe toute `Exception`, et les étapes 4 et 6 toute `OSError` : cette fonction est l'endroit le plus simple où une panne atteint l'étape 7 pendant que l'écoute du tailnet est servie. Une `RuntimeError` de `create_server` ou de `start_serving` l'atteint aussi, mais seulement pendant une reprise (deuxième cas ci-dessous).
    - Écoute du tailnet servie : ligne ERROR « surveillance des écoutes arrêtée : écoute du tailnet fermée », sans l'adresse ni trace. L'écoute du tailnet est fermée : son serveur a quitté `servers` et son port refuse les nouvelles connexions ; une connexion qu'elle avait déjà acceptée continue. Les écoutes de boucle locale continuent de servir.
    - Pendant une reprise du tailnet : une `RuntimeError` injectée dans `start_serving` du serveur du tailnet, déjà dans `servers` (étape 6) : même ligne ERROR, le serveur quitte `servers`, et le port est libre.
    - Écoute du tailnet en attente (runner qui ne confirme pas), puis panne à l'étape 2 sur une écoute de boucle locale : ligne ERROR « surveillance des écoutes arrêtée », sans un mot du tailnet ; même ligne quand aucune adresse du tailnet n'est configurée.
    - Dans chaque cas, l'arrêt qui suit se déroule normalement (`super().shutdown` appelé, ports libres).
  - **SIGTERM, sous-processus** : un script lance `serve` avec deux écoutes (boucle locale et « tailnet » ouvert par la tâche de surveillance), avec un WebSocket ouvert sur chacune. Sur SIGTERM, les deux WebSockets reçoivent 1012, le processus finit dans le délai et par le signal (code de retour −15 sous POSIX, comme `uvicorn.run`), sans « Cancel … running task(s) ». Les deux ports refusent ensuite la connexion. La tâche de surveillance, toujours vivante après la reprise puisqu'elle continue de surveiller, est annulée avant `Shutting down` (ligne DEBUG de son annulation, lue avant `Shutting down`). Test POSIX seulement (ignoré sous Windows).
- **`Host` (PR B).** L'adresse d'écoute en `Host` (`100.101.102.103:8765`, `[fd7a:115c:a1e0::1]:8765`) est admise ; une autre adresse du tailnet ne l'est pas.
- **Interface (Vitest).** Une demande de ticket précède chaque `open`, reconnexions comprises, et chaque `open` reçoit `['nexus.live.v1', ticket]` avec un ticket différent ; l'URL ne contient jamais `nxw_`. 401 sur la demande avec application verrouillée : aucune socket, aucune nouvelle demande jusqu'au déverrouillage, puis une connexion immédiate. **401 sans verrouillage** (jeton remplacé par un autre onglet entre l'envoi et la réponse) : nouvelle demande après le backoff, avec le nouveau jeton, et jamais d'attente d'un déverrouillage. Erreur réseau : backoff croissant. `stop()` pendant la demande : requête annulée, aucune socket. Réponse de ticket mal formée : traitée comme un échec, jamais ouverte. Fermeture 4401 : nouvelle demande de ticket.
- **Bout en bout (Playwright).** Les specs existantes (temps réel compris) passent avec le ticket ; `auth.spec.ts` : un jeton révoqué pendant que l'interface est ouverte la verrouille et la connexion temps réel se ferme. Les traces Playwright contiennent des tickets consommés d'une base jetable : sans valeur, et le hook de pré-commit bloque déjà ces artefacts.

## 7. Risques résiduels

- **Niveaux DEBUG et TRACE** : toute bibliothèque qui écrit ses en-têtes, ses traces d'exception ou son scope à ces niveaux (websockets et uvicorn aujourd'hui, une autre demain) peut contourner le filtre. Les tests en DEBUG et en TRACE sur vrai serveur sont le garde-fou, à relancer à chaque montée de version d'uvicorn ou de websockets.
- **CGNAT** (remarque de CodeRabbit) : une adresse `100.64.0.0/10` qui n'est pas celle de Tailscale passerait la seule validation de plage de D9 (a), et la reprise de D10 aurait lié Nexus **tout seul** à une autre interface qui reçoit plus tard la même adresse (partage de connexion mobile, opérateur en CGNAT). **Fermé par le contrôle auprès de Tailscale** décidé par Loïc le 2026-10-13 (D9, §3.7) : pas de bind sans confirmation (état `Running` et adresse donnée à ce nœud), une écoute dont l'adresse n'est plus confirmée est fermée, et une écoute que la surveillance ne contrôle plus, parce que sa tâche s'est arrêtée sur une erreur imprévue, est fermée aussi (§3.7, étape 7). Ce qui reste : le contrôle fait confiance au binaire `tailscale` et au démon locaux (limite d'ADR-020 D5) ; une adresse qui change de main juste après un contrôle reste écoutée jusqu'au contrôle suivant : environ 30 s en pratique, 42 s au plus (intervalle de 30 s et deux contrôles de 6 s au plus, §3.7, « Cas limites ») ; un Tailscale absent ou lent garde l'écoute du tailnet fermée (échec fermé, signalé en WARNING). La règle de pare-feu par interface (§1) ferme aussi cette fenêtre, si elle est posée : elle reste recommandée, pas imposée par le code.
- **Modèle d'hôte faible** (§1) : sans règle de pare-feu, un pair du réseau local atteint l'écoute du tailnet en clair sous Linux. Le contrôle auprès de Tailscale n'y change rien : il dit à qui appartient l'adresse, pas par quelle interface arrive un paquet. Sous Windows, le modèle d'hôte fort l'empêche par défaut, sauf routage ou `WeakHostReceive` activés ; le contrôle sur Helios reste à faire, et rien n'attend son résultat (Loïc, 2026-10-13). Une règle « python.exe » créée par l'invite de la première écoute sur le profil Privé annule la règle par interface si le Wi-Fi de la maison est classé Privé ; les règles de blocage que la même invite crée sur le profil Public ferment le tailnet si l'interface Tailscale est classée Public (§1, à vérifier sur Helios). Les jetons et les tickets protègent les données dans tous les cas.
- **Port de la boucle locale pris pendant une reprise** (§3.7) : si une écoute de boucle locale meurt en service (cas proactor de Windows) et qu'un autre processus local prend le port avant la reprise, les clients locaux (proxy Vite) lui envoient le jeton porteur de Loïc. Au démarrage, ce cas est fatal ; en service, Nexus ne peut que l'écrire en WARNING (`EADDRINUSE`, une fois par changement d'état) et retenter toutes les 30 s. Un processus malveillant qui vise ce port relève déjà de la limite assumée d'ADR-020 D5 ; un processus innocent qui le prend par hasard recevrait quand même le jeton, d'où le message propre à `EADDRINUSE`.
- **Écho du refus 400 de websockets** (§3.6) : **exception à ADR-006** acceptée par Loïc le 2026-10-13 et inscrite sous ADR-006 par la PR A ; l'écho va à l'expéditeur seul, qui détient déjà le ticket. Un intermédiaire qui journaliserait les corps de réponse verrait un ticket à usage unique, encore valide 30 s au plus.
- **Adresse dans le journal d'`asyncio`** : sous la boucle proactor, la perte d'une écoute passe par le gestionnaire d'exceptions de la boucle (« Accept failed on a socket »), qui écrit la socket, donc l'adresse locale, sur le logger `asyncio`. Nexus ne l'intercepte pas : l'adresse du tailnet n'est pas un secret, et la règle « sans l'adresse » ne vaut que pour les messages de Nexus.
- **Intérieur d'uvicorn et des boucles** : la reprise et la surveillance de D10 utilisent `Server.servers`, `server_state`, `lifespan`, la signature de `http_protocol_class` et le fait qu'une écoute morte laisse sa socket à `fileno() == -1` (§3.7), rien de tout cela n'étant une API documentée. Une montée de version d'uvicorn, d'uvloop ou de Python peut les changer : les tests de reprise, d'écoute perdue et d'arrêt par SIGTERM doivent alors échouer, pas se taire. Le cas proactor n'est couvert que par un test unitaire ; le vrai comportement sous Windows n'est vérifié que sur Helios. En particulier, la reprise d'une écoute perdue alors que des connexions acceptées par elle restent ouvertes n'est pas vérifiée sous Windows, où `socket.create_server` ne pose pas `SO_REUSEADDR` (`socket.py:921-937`) : un nouveau bind peut échouer tant que ces connexions vivent, dont la WebSocket longue du proxy Vite. L'échec est alors écrit en WARNING une fois (§3.7), et l'écoute reste fermée (l'interface locale injoignable, si c'est la boucle locale) jusqu'à la fermeture de ces connexions ou un redémarrage. Contrôle à faire sur Helios (§2).
- **HTTP en clair** : sur le tailnet, WireGuard chiffre ; un `tailscale serve` ou un proxy ajouté plus tard journaliserait peut-être les en-têtes ; SECURITY le déconseille.
- **Un seul processus** : un futur déploiement à plusieurs processus devra passer à D4 (b).
- **Interface distante** : un navigateur d'un autre appareil n'appelle pas encore le REST (CORS #47) ; #57 ouvre surtout le tailnet aux agents des autres nœuds.
