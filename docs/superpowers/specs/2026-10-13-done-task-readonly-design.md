## 0. Constat

- `tasks/rules.py:24` autorise `done → in_progress` (« réouverture ») ; c'est la seule transition qui sort de `done` (`rules.py:18-26`).
- `tasks/service.py:139-144` refuse `evidence_missing_on_done` (« cette tâche est terminée sans preuve : rouvre-la pour joindre la preuve attendue », ligne 143) quand un `PATCH` pose une preuve attendue sur une tâche close sans preuve ; l'interface fait de même avant l'envoi (`web/src/tasks/TaskPane.tsx:216-220`, « rouvre-la pour exiger une preuve »).
- Hormis cette règle, `PATCH /api/tasks/<ref>` (`tasks/api.py:238-243`, `service.update_task`, `service.py:110-163`) modifie librement une tâche `done` : titre, objectif, agent principal, collaborateurs, prochaine action, dates, priorité. Les dépendances aussi : `add_dependency` accepte une dépendance traitée sur une tâche close (`service.py:305-312`), `remove_dependency` n'a aucune règle (`service.py:331-337`).
- `reopen_with_advanced_dependents` (`service.py:193-201`, miroir `web/src/tasks/moves.ts:24-36`) ne joue qu'en sortant d'un statut traité (`done` ou `dropped`, `rules.py:32`) : sans réouverture de `done`, il ne reste que `dropped → backlog`.
- Côté agents (`events/service.py:483-582`) : `claimed` et `handoff` passent par `update_task` et s'appliquent aujourd'hui à une tâche close ; `working` d'un nouveau run la rouvre (`move("in_progress")`, ligne 554) ; `blocked` et `review` sont refusés avec « passage de done à … non autorisé » ; `done` donne « déjà en done » (lignes 525-535), sans joindre ses preuves (seul `review` les joint quand la tâche y est déjà, lignes 526-531).
- Aucune route ne permet à un humain de joindre une preuve sans changer de statut : `service.attach_evidence` (`service.py:318-328`) n'est appelé que par les effets d'événements (`events/service.py:528`), et il ne masque pas les secrets lui-même (les preuves d'un événement le sont déjà dans `publish`, `events/service.py:180-186`). Il dépouille chaque preuve par `str.strip` (`service.py:320`), alors que l'API et `publish` utilisent le dépouillement de Pydantic (`API_STRIP`, `events/service.py:106`, appliqué ligne 163) : les deux ne retirent pas les mêmes caractères (`"\x1c"` est retiré par `str.strip`, gardé par Pydantic ; vérifié).
- Dans `move` (`events/service.py:517-539`), « déjà dans ce statut » est jugé une fois, avant `attempt` ; après un `StaleDataError`, `attempt` relit la tâche et rappelle `change_status`, qui lève `same_status`. Sur ce chemin, la preuve d'un `review` qui perdrait sa course contre un passage en `review` par Loïc serait perdue (le chemin sans course la joint, lignes 526-531). **Ce chemin n'est pas atteignable en production.** L'insertion de l'événement (`session.add(event)` puis `flush`, lignes 265-267) est une écriture de la transaction de `publish`. Pour `working`, le verrou de sérialisation écrit même avant (ligne 243). SQLite garde ce verrou d'écriture jusqu'au commit, et `_apply_effects` (ligne 276) s'exécute après : aucune autre écriture ne peut être validée entre le `session.refresh(task)` de `move` (ligne 524) et l'`UPDATE` de `change_status`. Vérifié dans le venv du projet : une seconde session qui écrit sur la tâche pendant qu'une première a écrit sans valider reçoit `OperationalError` « database is locked » ; la première relit ensuite la tâche inchangée. Le `StaleDataError` d'un effet ne s'obtient que par injection, comme dans `test_effect_gives_up_after_repeated_version_conflicts` (`tests/test_events_api.py:1015`) et les tests de course de `tests/test_approvals_answer.py` (`race_hook`, ligne 575).
- Verrou optimiste : `Task.version` (`models.py:67-70`) ; un `UPDATE` fondé sur une version périmée lève `StaleDataError`, rendu en 409 `concurrent_update` (`app.py:143-149`) et retenté par les effets d'événements (`events/service.py:487-515`).
- La carte affiche « Ensuite : … » dès qu'il y a une prochaine action, quel que soit le statut (`TaskCard.tsx:39-44`).

## 1. Décisions de Loïc (2026-10-13, « Ok 65 »)

1. Sur une tâche `done`, seuls les commentaires restent modifiables ; les preuves peuvent encore être complétées, puisqu'elles ne changent pas ce qui a été fait.
2. Un lien facultatif « suite de nx-task-N » va de la tâche qui corrige vers l'ancienne. Nouveau champ, donc nouvelle migration.
3. `dropped → backlog` (reprise explicite) reste permis.
4. Les tâches déjà `done` passent en lecture seule ; les dépendances sur elles restent résolues.
5. Une entrée dans `DECISIONS.md`. La PR qui la contient, comme la migration, ne se fusionne que sur un « fusionne » de Loïc.

## 2. Règle serveur

**Recommandation : un seul code, `task_done` (409), pour toute mutation refusée sur une tâche `done`, contrôlé là où la mutation a lieu et seulement si elle change quelque chose.**

Message unique, constante `rules.DONE_IS_FINAL` : « tâche terminée : elle ne se modifie plus ; commente-la, joins-lui une preuve ou ouvre une tâche de suite ». Il ne contient aucune valeur reçue. Il ne commence ni par « déjà en » ni par « la tâche est déjà en » et ne finit pas par « est déjà l'agent principal » : `demo_agent.landed` (`demo_agent.py:325-326`) le lit donc comme un refus, jamais comme « déjà fait ».

Nouvelle fonction pure `rules.check_not_done(status)`, appelée par :

| Chemin | Comportement sur une tâche `done` |
|---|---|
| `rules.check_transition` | ordre : `unknown_status`, `same_status` (`done → done` reste « la tâche est déjà en done »), puis `task_done` pour toute autre cible ; `TRANSITIONS["done"]` devient `frozenset()` (`rules.py:24`) |
| `service.change_status` | `permissions.check_status` reste en premier : un agent qui vise `dropped` reçoit toujours 403 `human_only` (droit avant état, ADR-020 D8) ; le bloc `reopen_with_advanced_dependents` (`service.py:193-201`) reste, pour `dropped → backlog` seulement (commentaire mis à jour) |
| `service.update_task` | ordre inchangé jusqu'au calcul du diff : `not_updatable`, `permissions.check_update` (403 avant 409), masquage. Le diff est calculé **avant** tout `setattr` ; diff vide → 200, rien d'écrit, pas d'historique, `updated_at` inchangé (même contrat qu'aujourd'hui, `service.py:133-134`) ; diff non vide et tâche `done` → `task_done`, rien d'écrit. La règle `evidence_missing_on_done` (`service.py:139-144`) disparaît : elle ne peut plus jouer. Tous les champs de `UPDATABLE` (`service.py:27-31`) sont concernés, `next_action`, `lead_agent`, `collaborators` et `operation_role` compris (`role_not_applicable` n'est plus atteint sur `done`). `follows` entre dans `UPDATABLE` mais pas dans la boucle générique `getattr`/`setattr` (`service.py:125-129`) : ce n'est pas un attribut de `Task`. Il est comparé **en entier** sur `follows_id`, voir « `follows` dans `update_task` » ci-dessous |
| `service.add_dependency` (tâche close = celle qui dépend) | `self_dependency`, puis lien déjà posé → 204 sans effet (contrat existant d'un `PUT` répété), puis `task_done`. Ajouter une dépendance **vers** une tâche close depuis une autre tâche reste permis : seule l'autre tâche change, et la tâche close est traitée |
| `service.remove_dependency` (tâche close = celle qui dépend) | lien absent → 404 (contrat existant d'un `DELETE` répété), puis `task_done`. Retirer une dépendance d'une autre tâche vers une tâche close reste permis |
| `service.add_comment` | permis (décision 1) |
| `service.attach_evidence` | permis sur tout statut (§3) |

Un `PATCH` qui ne change rien sur une tâche close répond 200 et n'écrit rien, comme sur toute tâche (règle « ne contrôle que ce qui change » d'ADR-020, `DECISIONS.md:180`, étendue à cette règle d'état) ; un corps vide `{}` aussi. Une exception assumée : un secret recollé dans un champ déjà masqué laisse une ligne `secret_redacted` dans l'historique (`service.py:130-132`), sans changer aucun champ. C'est une trace de sécurité, pas une modification.

**`follows` dans `update_task`.** Le motif de l'API (§4) accepte des zéros en tête (`nx-task-0007`) : comparer le texte reçu au texte stocké verrait un changement là où il n'y en a pas. Ordre, dans le diff calculé avant tout `setattr` :
1. forme : la référence est lue en entier (`int` des chiffres après `nx-task-`), ou `None` pour `null` ; une forme invalide donne `invalid_follows` (appel direct ; l'API a déjà rendu 422) ;
2. comparaison de cet entier à `task.follows_id` : s'ils sont égaux, `follows` n'entre pas dans le diff ;
3. diff vide → 200, rien d'écrit (règle générale ci-dessus) ;
4. diff non vide et tâche `done` → `task_done`, **sans chercher la cible** ;
5. cible cherchée seulement ensuite : absente → 404 `not_found` ; présente mais pas `done` → 409 `follows_not_done` (§4) ;
6. écriture de `follows_id`, et historique `{"follows": [avant, après]}` reformaté à partir des entiers (`nx-task-<n>` ou `null`), jamais à partir du texte reçu.

Ainsi, `PATCH {"follows": "nx-task-07"}` sur une tâche qui suit déjà nx-task-7 a un diff vide : 200 même si la tâche est `done`, sans ligne d'historique et avec `updated_at` inchangé. `create_task` lit la référence de la même façon (`created` porte `"follows": [null, "nx-task-7"]` pour `nx-task-0007`).

*Pourquoi `task_done` avant 404 :* la cible est le contenu du corps, alors que la tâche modifiée est la ressource de l'URL, déjà résolue (404 si elle n'existe pas). On juge l'état de la ressource visée avant ce que le corps désigne. Sur une tâche close, l'écriture est refusée quelle que soit la cible, et la chercher ne servirait à rien. « Droit avant état » (ADR-020 D8) ne tranche pas ce cas : il ordonne deux contrôles portant sur le même objet, et le lien n'a aucun contrôle de droit (§4). Les dépendances ne contredisent pas cet ordre : `PUT …/dependencies/<other>` rend 404 avant `task_done` parce que `<other>` est dans l'URL et que la route le résout avant le service (`tasks/api.py:279-291`), pas parce que l'existence passerait avant l'état.

`next_action` n'est pas effacée au passage en `done` : l'historique garde ce qui était prévu ; seule l'interface cesse de l'afficher (§5).

*Alternatives écartées :*
- garder `transition_refused` pour les statuts et un autre code pour `PATCH` : deux messages pour une même règle, et « passage de done à in_progress non autorisé » n'indique pas quoi faire ;
- refuser tout `PATCH` sur `done`, même sans changement : contredit la règle d'ADR-020 et casse l'interface, qui renvoie les champs qu'elle croit modifiés.

### Concurrence

Pas de nouveau verrou : la règle s'appuie sur `Task.version`. Toute mutation refusée sur `done` écrit la ligne `tasks` de la tâche visée (`update_task`, `add_dependency` et `remove_dependency` posent `updated_at`, `attach_evidence` aussi), donc son `UPDATE … WHERE version = :lue` échoue si une transition vers `done` a été validée entre la lecture et l'écriture. Statut et version changent dans le même `UPDATE` : une écriture qui passe a jugé le statut sur la version courante.

- `PATCH` contre `POST …/status done` : course **atteignable**. La route lit la tâche hors transaction et n'écrit qu'au commit, donc une clôture peut être validée entre les deux. Le perdant reçoit 409 `concurrent_update` ; relancé, il reçoit 409 `task_done`. On ne rejoue jamais le `PATCH` perdant (checklist §3).
- Effets d'événements : course **inatteignable en production** (§0). Quand `_apply_effects` s'exécute, l'insertion de l'événement, ou pour `working` le verrou de sérialisation, tient déjà le verrou d'écriture de SQLite jusqu'au commit. Le `session.refresh(task)` de `move` voit donc l'état final de la tâche, et aucune clôture ne peut s'intercaler. Les contrôles ci-dessous sont gardés **par défense** : ils coûtent peu, et ils tiendraient si une écriture devait un jour précéder la lecture autrement (autre base, autre ordre dans `publish`). `attempt` relit la tâche après un `StaleDataError` et retente (`events/service.py:501-503`) ; la nouvelle tentative voit `done` et consigne `task_done`. Pour `review` et `done`, elle juge aussi « déjà dans ce statut » (sous-section suivante). Ces chemins ne se testent que par injection d'un `StaleDataError` (§7), comme `test_effect_gives_up_after_repeated_version_conflicts` (`tests/test_events_api.py:1015`).
- Lien de suite à la création (§4) : la cible doit être `done`, et `done` est désormais absorbant. Une cible lue `done` le reste ; une cible lue non close est refusée, ce qui est juste à cet instant. Aucun verrou sur la cible, qui n'est pas modifiée.
- Le verrou de sérialisation de `working` (`events/service.py:232-251`) touche la ligne d'une tâche close puis rend son `updated_at` quand aucun effet n'est appliqué (lignes 288-291) : seule `version` avance, comme aujourd'hui pour tout `working` sans effet.

### Événements d'agents sur une tâche `done`

Un événement reste toujours enregistré (EVENT-PROTOCOL §6 bis). L'ordre de `move` (`events/service.py:517-539`) ne change pas : run périmé d'abord (raisons existantes inchangées, `_stale_run`, lignes 455-480), puis « déjà dans ce statut », puis la transition. Pour `claimed` et `handoff`, qui passent par `update_task`, l'ordre est celui d'`update_task` : `permissions.check_update` (droit, ADR-020 D8, `DECISIONS.md:176`), puis diff vide (pour `handoff` : « … a déjà la main, avec la même prochaine action »), puis `task_done`. Un `claimed` de l'agent principal ne tente rien (`events/service.py:544`).

**« Déjà dans ce statut » jugé à chaque tentative (défense, voir « Concurrence »), et la preuve dans un `attempt` à elle.** Le test `task.status == target` de `move` passe dans la fonction retentée par `attempt("status:<cible>", …)`. À chaque tentative, sur la tâche relue, soit la tâche est déjà dans le statut visé, soit `change_status` est appelé. Dans le premier cas, la fonction n'écrit rien et le signale à `move`, par exemple en renvoyant « déjà là » au lieu de lever une exception. `move` consigne alors l'effet de statut, puis joint les preuves **par un second `attempt("evidence", lambda: tasks.attach_evidence(…))`**, avec son propre point de sauvegarde :
- `done` sur `done` : effet `status:done` non appliqué, « déjà en done » ; puis, s'il y a des preuves, effet `evidence`, appliqué ou non appliqué avec la raison d'`attach_evidence` ;
- `review` sur `review` avec preuves : **aucun** effet `status:review`, seulement l'effet `evidence` (forme actuelle, lignes 526-531) ;
- `review` sur `review` sans preuve, et `done` sur `done` sans preuve : le seul effet « déjà en <cible> ».

L'`attempt` séparé n'est pas un détail d'écriture. Si `attach_evidence` était appelé dans la fonction retentée de `status:done`, son refus `evidence_unchanged` (une `RuleViolation`) serait attrapé par cet `attempt` et consigné comme un **seul** effet `{"action": "status:done", "applied": false, "reason": "evidence : déjà jointe à la tâche"}`. `landed` (`demo_agent.py:314-327`) ne reconnaît que « déjà en … » ou un effet appliqué, donc il lirait ce refus comme un échec : code 4, là où un `done` renvoyé sur une tâche déjà close avec la même preuve rend 0 aujourd'hui. Avec deux effets, `landed` trouve `status:done` « déjà en done » et ignore `evidence`, qui n'est pas l'action attendue : code 0. Les effets consignés sont les mêmes avec ou sans `StaleDataError` injecté.

| Kind | Aujourd'hui | Après |
|---|---|---|
| `claimed` d'un autre agent que l'agent principal | appliqué | `lead_agent` non appliqué, raison `DONE_IS_FINAL` |
| `claimed` de l'agent principal | aucun effet (`effects` vide) | inchangé |
| `working` d'un nouveau run | **appliqué : rouvre la tâche** | `status:in_progress` non appliqué, raison `DONE_IS_FINAL` ; le run est quand même ouvert (le fait est enregistré) et se clôt comme tout run |
| `working` d'un run clos | « le run … est déjà clos … » | inchangé |
| `blocked` | « passage de done à blocked non autorisé » | raison `DONE_IS_FINAL` |
| `review`, et `done` sans preuve (enregistré en `review`) | « passage de done à review non autorisé » | raison `DONE_IS_FINAL` ; preuves non jointes |
| `done` avec preuves | `status:done` « déjà en done », preuves ignorées | `status:done` « déjà en done » (inchangé), **plus** un effet `evidence` distinct (son propre `attempt`) : appliqué si une preuve nouvelle est jointe, sinon non appliqué avec la raison de `attach_evidence` (« evidence : déjà jointe à la tâche », « evidence : aucune preuve lisible », ou un refus de forme du §3) |
| `handoff` d'un exécutant vers un autre agent que l'agent principal | non appliqué, `assign_forbidden` (« lead_agent : un exécutant ne peut désigner que lui-même, un humain ou personne ») | inchangé : le droit passe avant l'état |
| `handoff` identique (même agent principal, même prochaine action) | non appliqué, « X a déjà la main, avec la même prochaine action » | inchangé : rien ne change, `update_task` n'écrit rien |
| autre `handoff` (vers un humain, ou vers l'agent principal actuel avec une nouvelle prochaine action) | appliqué | non appliqué, raison `DONE_IS_FINAL` |
| `progress`, `failed`, `question`, `needs_human`, `unknown` | aucun changement d'état | inchangé ; une demande adressée à un humain ouvre toujours son approbation |

Pour `handoff`, le run périmé passe toujours en premier (`events/service.py:568-571`), et `handoff_to_self` reste un 409 avant tout effet. Seules les raisons de `blocked` et `review` changent de texte parmi les refus existants.

Si Loïc clôt la tâche pendant le run de l'agent, le `done(r1)` de l'agent reçoit l'effet « déjà en done », que `landed` accepte (code 0), plus l'effet `evidence` : ses preuves sont jointes, ou l'effet `evidence` est non appliqué (« déjà jointe ») si Loïc a clos avec la même preuve ; dans les deux cas, le code est 0. En production, la clôture de Loïc précède forcément l'insertion de l'événement, ou attend son commit (« Concurrence ») ; le cas d'une clôture validée pendant la tentative de l'agent n'existe que par injection et donne les mêmes effets.

**`demo_agent` : relancé sur une tâche close, il sort désormais avec le code 4** (aujourd'hui 0 : `working` rouvre la tâche, puis `done` la referme). Recommandation : `play` (`demo_agent.py:340`) lit déjà la tâche avant tout envoi ; s'il la trouve `done`, il s'arrête aussitôt avec le code 4 et le message « nx-task-N  tâche terminée : elle ne se modifie plus ; rien n'est publié (ouvre une tâche de suite) », sans `PATCH`, sans `claimed`, sans run. Sans ce contrôle :
- tâche close sans prochaine action : le `PATCH next_action` (`demo_agent.py:347-351`) reçoit 409 `task_done`, `call` lève `SystemExit` avec le message et l'agent sort avec le **code 1**, pas 4 (vérifié) ;
- avec une prochaine action : `working` est enregistré et refusé (`DONE_IS_FINAL`), puis l'agent clôt son run par un `failed` (`demo_agent.py:390-394`) : code 4, mais trois événements pour un refus prévisible.

Une clôture entre la lecture et l'envoi reste couverte par le chemin existant (`landed` lit le refus, code 4 après clôture du run), sauf la fenêtre entre le `GET` et le `PATCH next_action`, qui donne le code 1 (« requête refusée », 4xx) : documenté, pas traité. Une tâche `dropped` garde le comportement actuel (`working` refusé, code 4). EVENT-PROTOCOL §6 bis (`EVENT-PROTOCOL.md:168`, paragraphe « Exemples exécutables ») le dit : le code 4 vaut aussi pour une tâche déjà terminée, sur laquelle rien n'est publié, et une relance sur une tâche close ne la rouvre plus ; le commentaire de `EXIT_EFFECT_REFUSED` (`demo_agent.py:48`) aussi.

*Alternative écartée :* aucun effet sur une tâche close, preuves comprises (lecture stricte de l'issue). Un agent qui finit après la clôture par Loïc perdrait ses preuves, alors que la décision 1 les accepte ; les agents parlent par événements (ADR-015), pas par une route de tâche.

## 3. Compléter les preuves d'une tâche close

**Recommandation : une route dédiée `POST /api/tasks/<ref>/evidence`, ajout seul.**

- Corps `EvidenceIn(InputModel)` : `evidence: list[Ref]`, au moins un élément ; `Ref` est la contrainte de `events/api.py:34` (texte dépouillé de ses espaces, non vide, `EVIDENCE_REF_MAX` = 512 caractères, `events/limits.py:13`). Réponse 200 avec la tâche (`TaskOut`, `source` et `measured_at`).
- Service : `attach_evidence` devient sûr pour tout appelant direct (checklist §2). Dans l'ordre :
  1. liste de textes exigée (`invalid_evidence`, un tuple est normalisé) ;
  2. **valeur non encodable refusée** : `has_unencodable(evidence)` (`nexus/validation.py:32`) → `RuleViolation("invalid_value", "valeur non encodable : demi-paire UTF-16, NaN ou Infinity")`, même code et même message que `publish` (`events/service.py:170-175`) et `approvals/service.py:227-229`. L'API le refuse déjà en 422 (`InputModel`) ; sans ce contrôle, une demi-paire UTF-16 passée par un appel direct serait stockée et ferait échouer chaque lecture de la tâche ;
  3. dépouillement (point suivant), puis longueur re-contrôlée (`too_long_evidence`, même mesure que l'API) ;
  4. **masquage des secrets** par `secrets.redact_fields` et trace `secret_redacted` (`_record_redactions`) ;
  5. filtre `is_blank_reference`.

  Les preuves d'un événement, déjà masquées, ne laissent pas de seconde trace.
- Dépouillement (checklist §2, « mesurer ce qui sera stocké ») : `e.strip()` (`service.py:320`) cède la place au dépouillement de Pydantic, `API_STRIP.validate_python(e)`, comme `publish` (`events/service.py:163`). Une preuve jointe par un événement, par la route ou par un appel direct est alors stockée à l'identique, et `evidence_unchanged` la reconnaît. `tasks/service.py` ne peut pas importer `events/service.py`, qui l'importe déjà : `API_STRIP` passe dans `nexus/validation.py` (déjà partagé, `has_unencodable`), et `events/service.py` le réimporte sous le même nom (`approvals/service.py:231` lit `events.API_STRIP`). Même changement pour le calcul identique de `change_status` (`service.py:230`), sinon une même preuve passée par `POST …/status` et par la nouvelle route serait stockée deux fois.
- Codes existants conservés : 409 `evidence_required` (aucune preuve lisible), 409 `evidence_unchanged` (rien de nouveau). L'historique garde `updated` `{"evidence": [avant, après]}` (`service.py:328`), ce qui est réellement stocké.
- Permis sur tout statut et pour tout acteur authentifié, comme commenter : le service l'est déjà, et une preuve ne change ni le statut ni l'assignation. SECURITY §3 ajoute « joindre une preuve » à la ligne « Lire, commenter, lier ou délier… ». L'interface ne l'offre que sur une tâche close dans cette PR (sur une autre, la boîte de déplacement vers `done` demande déjà la preuve).
- Une tâche `done` sans preuve (aucune preuve jointe, qu'une preuve soit attendue ou non) n'est ni rouverte ni déplacée : elle reste `done`, et sa preuve se joint ensuite. C'est exactement le point 10 de VIEWS §8 (« Terminé sans preuve (done sans evidence) ») : sa détection ne change pas, son action proposée devient « joindre une preuve » ou « ouvrir une tâche de suite », jamais « rouvrir ». Le détecteur d'oublis n'existe pas encore dans le code : seule la ligne de VIEWS change.
- Course avec un agent qui joint la même preuve : la seconde écriture reçoit 409 `evidence_unchanged` (« evidence : déjà jointe à la tâche »), ou 409 `concurrent_update` si les deux se croisent, puis `evidence_unchanged` à la relance. L'interface affiche le message sous le formulaire et garde le texte saisi (§5).

*Alternatives écartées :* `PATCH` limité à `evidence` (un `PATCH` remplace un champ : il permettrait de retirer une preuve, ce qui change ce qui a été prouvé, et sa comparaison d'une liste brouille « ne contrôle que ce qui change ») ; `POST …/status` vers `done` avec `evidence` sur une tâche déjà close (c'est `same_status` : une transition qui n'en est pas une).

## 4. Lien « suite de »

**Recommandation : colonne `tasks.follows_id`, exposée comme `follows` (`"nx-task-<n>"` ou `null`), posée par la tâche qui corrige, vers une tâche `done` seulement.**

- **Nom.** `follows` dans l'API et l'interface (« suite de »), `follows_id` en base (comme `depends_on_id`). Écartés : `continues` (ambigu : continuer n'est pas corriger), `follows_task_id` (redondant avec la référence `nx-task-`).
- **Facultatif.** `NULL` par défaut ; aucune tâche existante n'en reçoit (pas de rétroremplissage : rien ne permet de deviner un lien).
- **Cible.** Doit exister : sinon **404 `not_found`**, message `nx-task-N` reformaté par `get_task` à partir de l'entier lu (`tasks/service.py:45-49`), jamais la valeur reçue. C'est le comportement existant pour toute référence de tâche bien formée qui ne désigne rien, y compris dans un corps : `task` d'un événement (`publish` → `_task` → `TaskNotFound`, `events/service.py:359-362`) et `PUT …/dependencies/<ref>`. Un 409 annoncerait une règle d'état (ADR-020 D8) là où il n'y a rien à juger ; le code `follows_unknown` est abandonné. Quand la tâche modifiée par un `PATCH` est `done`, `task_done` passe avant ce 404 et la cible n'est même pas cherchée (§2). La cible doit aussi être `done` (409 `follows_not_done`, « follows : nx-task-N n'est pas terminée ; une tâche de suite ne suit qu'une tâche terminée », référence reformatée par le serveur à partir de l'entier lu). `dropped` est refusé aussi : une tâche abandonnée peut être reprise (`dropped → backlog`), le lien perdrait son sens et les cycles redeviendraient possibles.
- **Validation de la référence.** API : `follows: Annotated[str, StringConstraints(pattern=r"^nx-task-[0-9]{1,12}$")] | None` (422 sans recopie, `french_errors`). Service (appel direct) : texte exigé, `re.fullmatch` ASCII strict comme `parse_ref` (`tasks/api.py:34-40`), sinon `RuleViolation("invalid_follows", "follows : référence de tâche invalide")`. Le motif admet des zéros en tête (`nx-task-0007`) : la référence est convertie **une fois** en entier par une fonction du service (comme `int(raw)` dans `parse_ref`), et tout le reste travaille sur cet entier. La comparaison au lien actuel se fait sur `follows_id`, la recherche de la cible passe par `get_task`, et le texte de l'historique est reformaté à partir de l'entier. Le texte reçu n'est jamais stocké, comparé ni recopié.
- **Après la création.** Oui, par `PATCH {"follows": …}` (poser, changer, retirer avec `null`) tant que la tâche qui porte le lien n'est pas `done`. Sur `done` : `task_done` si l'entier diffère de `follows_id`, 200 sinon (`"nx-task-07"` sur une tâche qui suit nx-task-7 ne change rien). Ordre des contrôles, détaillé au §2 (« `follows` dans `update_task` ») : forme, diff, `task_done`, puis seulement existence de la cible (404) et son statut (`follows_not_done`). Le `PATCH` pose `updated_at` de cette tâche : même verrou de version que le reste. Aucun contrôle de droit : ce n'est pas une assignation. L'interface ne pose le lien qu'à la création dans cette PR (§5) ; le changer ou le retirer passe par l'API.
- **Clé étrangère.** `REFERENCES tasks(id) ON DELETE SET NULL`, comme `events.task_id` (`models.py:131`) : une tâche de suite survit à son ancienne tâche, et l'historique garde la référence en texte. Aucune route ne supprime une tâche (SECURITY §3) : le cas reste théorique. Index `ix_tasks_follows_id` pour la lecture inverse.
- **Cycles.** Impossibles sans contrôle dédié : un lien n'est posé que par une tâche non close (`task_done` sinon) vers une tâche close, et `done` est final. Si A suit B puis B suivait A, B aurait été close quand A a posé son lien et non close quand B a posé le sien, après : contradiction. Se suivre soi-même revient à viser une tâche non close (`follows_not_done`). Une chaîne A ← B ← C (C suit B, close, qui suit A, close) est permise ; plusieurs tâches peuvent suivre la même.
- **Pas une dépendance.** `follows` n'entre ni dans `depends_on`, ni dans `GATED_BY_DEPENDENCIES`, ni dans `_pending_dependencies` ; il ne bloque rien (sa cible est close de toute façon) et ne se gère pas par `PUT …/dependencies`.
- **API.** `TaskCreate.follows`, `TaskUpdate.follows`, `TaskOut.follows` (calculé dans `to_out`, `tasks/api.py:183-189`, puisque `follows` n'est pas un attribut de `Task`). Pas de `followed_by` dans `TaskOut` : l'interface le calcule depuis la liste complète qu'elle a déjà (`WorkView.tsx:127` passe `all`), et `to_out` fait déjà une requête par tâche pour `depends_on`.
- **Historique.** À la création : `created` porte `"follows": [null, "nx-task-N"]` (les autres champs y sont déjà, `service.py:103-105`). Après : `updated` `{"follows": [avant, après]}`. Les deux valeurs sont reformatées en `nx-task-<n>` à partir des entiers (`follows_id` avant et après), jamais recopiées du corps : `nx-task-0007` est consigné `nx-task-7`. `create_task` retire `follows` de `data` avant `Task(**data)` (ce n'est pas une colonne) et pose `follows_id`. Rien n'est écrit sur l'ancienne tâche, qui ne change pas ; le message temps réel `task_changed` de la nouvelle tâche invalide la liste complète (`liveUpdates.ts:24`), donc « suivie par » se met à jour dans le panneau ouvert.

### Migration `0006_task_follows.py`

- `upgrade` : `op.add_column("tasks", sa.Column("follows_id", sa.Integer(), sa.ForeignKey("tasks.id", ondelete="SET NULL")), inline_references=True)` puis `op.create_index("ix_tasks_follows_id", "tasks", ["follows_id"])`. Sans `inline_references=True`, `op.add_column` lève `NotImplementedError` (« No support for ALTER of constraints in SQLite dialect », `alembic/ddl/sqlite.py:77-82`) : la clé étrangère d'une colonne ajoutée n'a pas de règle de création implicite, Alembic refuse au lieu d'avertir. Vérifié dans le venv du projet (Alembic 1.20.0, SQLite 3.45.1, `PRAGMA foreign_keys=ON`) : avec `inline_references=True`, DDL émis `ALTER TABLE tasks ADD COLUMN follows_id INTEGER REFERENCES tasks (id) ON DELETE SET NULL`, `PRAGMA foreign_key_list(tasks)` donne `on_delete = SET NULL`, une valeur inexistante est refusée par la base ; `upgrade` depuis une base vide, depuis `0005` peuplée et depuis `0004`, puis `downgrade` et `upgrade` de nouveau, passent sans perte de ligne.
- `downgrade` : `op.drop_index(…)` puis `op.drop_column("tasks", "follows_id")`, qui émet `ALTER TABLE tasks DROP COLUMN` natif (SQLite ≥ 3.35 ; l'index doit tomber d'abord, sinon l'`ALTER` échoue). Les liens sont perdus au retour arrière ; les tâches, dépendances, commentaires, historique et événements restent intacts.
- **Pas de mode batch (`op.batch_alter_table("tasks")`), par prudence et parce que la voie native est plus simple.** Le mode batch recopie la table puis fait `DROP TABLE tasks` ; avec `PRAGMA foreign_keys=ON` (`db.py:46`), ce `DROP` vaut `DELETE FROM tasks` et déclenche les `ON DELETE CASCADE` de `task_dependencies`, `task_comments` et `task_history` et le `SET NULL` de `events.task_id`. Vérifié sur une copie peuplée en `0005` : après un `batch_alter_table` qui ajoute la colonne et sa clé, `tasks` garde ses lignes, mais `task_dependencies`, `task_comments` et `task_history` tombent à zéro. Ce n'est pas inévitable : dans `upgrade()`, la connexion n'est pas dans une transaction (`in_transaction` faux : le pilote `sqlite3` n'ouvre la transaction qu'au premier ordre d'écriture), et `PRAGMA foreign_keys=OFF` y prend effet (vérifié). Mais couper les clés serait une étape de plus à ne jamais oublier, à l'aller comme au retour, pour un résultat que `add_column(…, inline_references=True)` et `drop_column` natifs donnent directement. `env.py` configure `render_as_batch=True` pour l'autogénération : `0006` s'écrit à la main.
- Données existantes : toutes les lignes reçoivent `NULL` ; les tâches déjà `done` deviennent en lecture seule par la règle, sans réécriture. La sauvegarde automatique avant migration (`app.py:95-97`) s'applique.
- **Modèle : `follows_id: Mapped[int | None] = mapped_column(ForeignKey("tasks.id"), index=True)`, sans `ondelete`**, avec le commentaire « ON DELETE SET NULL is set in the database by migration 0006 (inline REFERENCES); SQLAlchemy does not reflect ON DELETE on a column-level reference, so declaring it here would make compare_metadata report a remove_fk/add_fk pair. » Raison, vérifiée : SQLAlchemy 2.1.1 ne relit pas `ON DELETE` d'une référence posée sur la colonne (`inspect(...).get_foreign_keys("tasks")` rend `options: {}`, alors que `PRAGMA foreign_key_list` donne `SET NULL`). Avec `ondelete="SET NULL"` dans le modèle, `compare_metadata` rend `remove_fk` puis `add_fk`, et deux tests existants échouent (vérifié) : `tests/test_actor_tokens_migration.py:56` et `tests/test_approvals_migration.py:93` (`test_the_migrated_schema_matches_the_models`). Sans `ondelete` dans le modèle, le diff est `[]` et les deux passent ; la base garde `ON DELETE SET NULL`. L'écart ne coûte rien : aucun `create_all` dans le code ni les tests (le schéma ne vient que des migrations), et aucune route ne supprime une tâche. `events.task_id` (`models.py:131-133`) garde son `ondelete` : sa clé, créée par `create_table`, est une contrainte de table, que SQLAlchemy relit.

*Alternatives écartées :* table de liaison `task_follow_ups` (réversible par `drop_table`, mais une jointure de plus pour un lien à une seule cible, et `add_column`/`drop_column` natifs suffisent) ; colonne sans clé étrangère (l'intégrité ne tiendrait qu'au code) ; `ON DELETE CASCADE` (supprimerait la tâche de suite) ou `RESTRICT` (bloquerait une future purge pour un lien informatif).

## 8. Découpage et ADR

**Une seule PR, `feat/65-done-task-readonly`.** La règle, la route de preuve, le lien et l'interface forment un tout : la règle seule laisserait l'interface proposer « En cours » sur une tâche close et dire « rouvre-la », et le remplacement de la réouverture est justement « joindre une preuve ou ouvrir une suite ». Le volume reste modeste (une règle, une route, une colonne, un panneau). Deux PR (règle, puis lien) demanderaient chacune un « fusionne » (la première pour `DECISIONS.md`, la seconde pour la migration) et deux tours de relecture pour un seul sujet.

Fichiers protégés touchés : `DECISIONS.md` et `server/src/nexus/migrations/versions/0006_task_follows.py`. **Fusion seulement sur un « fusionne » explicite de Loïc**, même quand toutes les autres conditions d'AGENTS.md sont remplies. Touchant une migration, un invariant et la concurrence, la PR passe par `architect` avant `implementer` (AGENTS.md, « Model routing »).

**ADR-022** (nouvel ADR, pas un ajout : aucun ADR ne porte les statuts de tâche, qui vivent dans DATA-MODEL §3). ADR-021 reste réservé à la PR B de #57 ; si cette PR passe avant, `DECISIONS.md` saute provisoirement de 020 à 022. Texte proposé :

> ## ADR-022 — Une tâche terminée ne se modifie plus ; on corrige dans une tâche de suite
>
> - **Date :** 2026-10-13 (décidé par Loïc, issue #65 ; conception : `docs/superpowers/specs/2026-10-13-done-task-readonly-design.md`)
> - **Contexte :** `done → in_progress` permettait de rouvrir une tâche close, donc de réécrire ce qui a été livré et prouvé ; l'interface invitait à rouvrir pour joindre une preuve, et un agent qui ouvrait un run sur une tâche close la rouvrait.
> - **Décision :** `done` est final. Aucune transition n'en sort ; ni champ, ni dépendance de la tâche, ni agent principal, collaborateurs ou prochaine action ne change (409 `task_done`, contrôlé seulement si la requête change quelque chose). Restent possibles : commenter, et compléter les preuves (ajout seul, `POST /api/tasks/<ref>/evidence`, ou `done` d'un agent avec preuve). Un problème trouvé ensuite se règle dans une nouvelle tâche, qui peut porter le lien facultatif `follows` (« suite de nx-task-N ») vers une tâche `done` seulement ; ce lien n'est pas une dépendance. `dropped → backlog` reste permis. Les tâches déjà closes passent en lecture seule sans réécriture, et les dépendances sur elles restent résolues. Les événements d'agents sur une tâche close restent enregistrés ; leurs effets sont consignés non appliqués avec la raison.
> - **Conséquences :** migration `0006` (colonne `tasks.follows_id`, clé étrangère `ON DELETE SET NULL`, index ; ajoutée par `add_column(…, inline_references=True)` et réversible par `drop_column`, sans mode batch, qui, clés étrangères actives, viderait les tables liées ; le modèle déclare la clé sans `ondelete`, que SQLAlchemy ne relit pas sur une référence de colonne) ; `reopen_with_advanced_dependents` ne concerne plus que `dropped → backlog` ; une erreur sur une tâche close ne se corrige plus en place ; `demo_agent` relancé sur une tâche close sort avec le code 4 sans rien publier.
> - **Statut :** accepté.

## 9. Choix de mise en œuvre (validés par Loïc le 2026-10-14, « Ok 65 bis »)

Loïc a retenu les trois recommandations.

1. **Preuves d'un agent sur une tâche close** : un `done` avec preuve les joint (§2). D'accord, ou aucune écriture par événement sur `done`, preuves comprises ? *Décidé : les joindre.* La décision 1 accepte des preuves sur une tâche close, et un agent qui finit juste après la clôture par Loïc les perdrait sinon ; il n'a pas d'autre voie que l'événement (ADR-015).
2. **« Ensuite : … » sur les cartes `dropped`** : masqué aussi ? (Hors issue, une ligne de code.) *Décidé : oui.* Une tâche abandonnée n'a pas plus de suite prévue qu'une tâche close ; la reprise (`dropped → backlog`) se fait dans le panneau, qui montre toujours la prochaine action.
3. **Lien posé après coup depuis l'interface** : l'API le permet (`PATCH`), l'interface seulement à la création. Suffisant pour cette PR ? *Décidé : oui.* Le cas courant est « ouvrir une tâche de suite » depuis la tâche close ; un sélecteur après coup ajouterait un formulaire et ses cas de données changeantes pour un besoin non exprimé.
