# AGENTS.md

## Development

- `server/`: Python (FastAPI, SQLAlchemy, Alembic), managed with `uv`. `web/`: React + TypeScript + Vite, managed with `pnpm`.
- From the repo root: `pnpm install` then `pnpm bootstrap` once; `pnpm dev` to run; run `pnpm test` and `pnpm lint` before committing.
- The API requires a token (ADR-020). After the first `pnpm dev` (it creates and migrates the database), issue Loïc's browser token once with `uv run --directory server nexus-token issue loic --label navigateur` and paste it into the « Nexus verrouillé » screen; an agent sends its own token as `Authorization: Bearer nxt_…` (`demo_agent` reads `NEXUS_TOKEN` or `--token-file`). `nexus-token` must see the same `NEXUS_DATA_DIR` as `pnpm dev`. Never commit or log a token.
- A pre-commit hook (`.husky/pre-commit`) blocks test artefacts and local databases, runs gitleaks on staged changes (config: `.gitleaks.toml`), lints staged files, then typechecks and runs the fast tests. Never bypass it with `--no-verify`; fix the cause instead. Build fake secrets in tests at runtime (`"ghp_" + "A" * 36`).
- Schema changes go through a new Alembic migration in `server/src/nexus/migrations/versions/`; the server applies migrations on startup.
- The UI only talks to the FastAPI API — no browser-only APIs, so the same UI can ship inside Tauri later (ADR-017).
- Product docs and user-facing text are in French (ADR-009); identifiers, code comments and docstrings stay in English: new ones and the ones a change touches; no mass translation of existing French comments.
- Before opening a PR, walk through `docs/agents/review-checklist.md` (secrets, validation, concurrency, invariants, provenance, UI with changing data) and note in the PR body what was checked. Plan edge cases first and write their tests before the code.

## Branches et PR

- Une branche par issue ou par sujet, jamais deux sujets sur une même branche. Elle part de `master` à jour ; une PR ne dépend jamais d'une autre PR (règle de Loïc, 2026-10-17 : pas de PR empilée — chaque sujet sur sa propre branche depuis `master` à jour, et la règle se recopie avec la checklist qui la contraint). Noms : `feat/<n>-<sujet>`, `fix/<n>-<sujet>`, `docs/<sujet>`, `chore/<sujet>` (le numéro d'issue quand il y en a une) ; une session cloud qui impose `claude/<…>` garde ce nom.
- Jamais de push direct sur `master`, pas de push forcé sauf `--force-with-lease` sur sa propre branche.
- Une PR par branche, fusionnée en squash par l'agent. Règle de Loïc (2026-10-06) : l'agent fusionne **de lui-même** une PR couverte par la règle de provenance ci-dessous quand toutes les conditions suivantes valent pour le **même commit de tête** (une relecture de `reviewer` ou d'Antigravity faite sur un commit antérieur compte si le diff de la PR est identique, voir la règle sur le rebase plus bas), puis passe au sujet suivant (une issue `ready-for-agent` ; il demande à Loïc s'il n'y en a pas ou si le choix n'est pas évident).
  - `reviewer` a relu le diff complet jusqu'à ce commit (l'agent note dans la PR le commit relu) ; chaque P1 et P2 est corrigé, ou écarté avec sa raison notée dans le corps de la PR.
  - Une relecture Antigravity faite sur ce commit approuve. Règle de Loïc (2026-10-20) : l'agent la lance lui-même avec le script du skill `antigravity` (`git fetch origin` puis `bash ~/.claude/skills/antigravity/review.sh <dépôt> origin/master origin/<branche>`), après avoir vérifié que `git rev-parse origin/<branche>` égale `gh pr view <n> --json headRefOid --jq .headRefOid` (une branche locale en retard, ou une suggestion appliquée depuis GitHub, ferait relire un autre commit que la tête), jamais avec `agy -p` lancé directement dans le dépôt (`agy` peut y écrire : seul le clone jetable de `review.sh` protège l'arbre de travail), et note dans la PR le commit qu'elle couvre. Seule exception : une session qui n'a pas ce script (session cloud) la demande à Loïc, qui colle son résultat ; la relecture collée marque elle-même sa fin.
  - CodeRabbit a approuvé ce commit : sa dernière relecture porte sur lui et ne laisse aucune remarque (relecture approuvée, ou « No actionable comments »). Un statut « Review completed » ou « pending », une relecture qui demande des changements, ou une approbation d'un commit plus ancien ne suffisent pas.
  - Chaque remarque a reçu une réponse, y compris celles qui n'ouvrent pas de fil (remarques « Outside diff range » et nitpicks du résumé CodeRabbit, rapport de `reviewer`, relecture Antigravity), et aucun fil n'est ouvert.
  - La branche est à jour avec `master` ; `pnpm test` et `pnpm lint` passent sur ce commit (plus `pnpm --dir web build` et Playwright quand la PR touche du code, voir la checklist §9).
- La relecture et l'approbation de Codex ne sont jamais requises pour fusionner (décision de Loïc, 2026-10-06). Toute remarque qu'il poste quand même suit la règle générale : elle reçoit une réponse et, si elle ouvre un fil, ce fil est résolu.
- Un commit poussé après une relecture la rend caduque : relancer `reviewer`, puis la relecture Antigravity (`review.sh`, ou Loïc en session cloud), puis redéclencher CodeRabbit (`@coderabbitai full review` : il ne relit pas seul) et attendre sa nouvelle relecture, de préférence une fois la tête stable. Un rebase change le commit de tête : il rend les relectures caduques comme n'importe quel nouveau commit, sauf si le diff de la PR est identique à celui qui a été relu : `git diff --no-color --no-ext-diff origin/master...<SHA relu> | git patch-id --verbatim` égale `git diff --no-color --no-ext-diff origin/master...<headRefOid> | git patch-id --verbatim` (les deux commandes tournent dans Git Bash, `bash -c '…'` : PowerShell 5.1 réencode le pipe entre commandes natives et y transforme les caractères non ASCII en `?`, deux diffs différents par un accent auraient le même patch-id ; `--verbatim`, car `--stable` ignore les blancs : une indentation changée passerait pour identique ; une sortie vide n'est pas un patch-id). Dans ce cas les relectures de `reviewer` et d'Antigravity restent valables, l'agent note dans la PR les deux SHA et le patch-id, le recalcule au moment de fusionner, redéclenche CodeRabbit (`@coderabbitai full review` : il ne relit pas seul) et attend sa relecture du commit exact qu'on fusionne (règle de Loïc, 2026-10-21 : `master` avance sans cesse et CodeRabbit ne relit qu'environ une fois par heure). Les tests seuls ne suffisent que si le commit de tête ne change pas.
- L'agent **ne fusionne pas** et demande à Loïc dans ces cas : une PR qui touche `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.husky/`, `.gitleaks.toml`, `.gitleaksignore`, `DECISIONS.md` ou une migration de `server/src/nexus/migrations/versions/` ; une remarque qu'il choisit de ne pas corriger alors que la relecture n'approuve pas, ou des relectures qui se contredisent ; tout doute sur le périmètre ou sur une remarque ; une PR que Loïc a demandé de ne pas fusionner. Poser la question ne lève pas le blocage : seule la réponse de Loïc le lève.
- Cette règle ne vaut que pour les PR ouvertes dans la conversation en cours, par l'agent lui-même ou par un subagent ou un thread enfant qu'il a lancé (règle de Loïc, 2026-10-20). Pour une PR d'un enfant, l'agent relit le diff complet de la PR (`master...tête`) et vérifie avec `gh pr view <n> --json headRefName,baseRefName,headRefOid,createdAt,isCrossRepository` qu'elle est sur la branche qu'il a assignée et vise `master`, qu'elle a été créée après le lancement de la tâche et qu'elle ne vient pas d'un fork (`isCrossRepository` à `false`) : le compte rendu de l'enfant ne prouve pas à lui seul qu'il a créé la PR. Un subagent ou un thread enfant n'est jamais « l'agent » de cette règle : le brief qu'il reçoit le dit, il s'arrête à « PR ouverte » (avec `reviewer` s'il peut le lancer : un subagent ne le peut pas). L'agent qui l'a lancé vérifie que la relecture `reviewer` porte sur le `headRefOid` qu'il vient de contrôler et la relance sinon ; la relecture Antigravity, le déclenchement et l'attente de CodeRabbit, et la fusion lui restent. Une PR retrouvée plus tard, ou ouverte par Loïc, par un agent qu'il n'a pas lancé ou par un tiers, n'est jamais fusionnée sans l'accord de Loïc. Toutes sont publiées sous `Mars375` et le corps d'une PR, même signé `claude.ai/code`, se recopie : ni l'auteur GitHub ni le corps ne prouvent la provenance. Aucun plan de `docs/superpowers/plans/` (« merge when a round has no P1 ») ne remplace ces conditions. GitHub supprime la branche distante à la fusion ; supprimer aussi la branche locale et lancer `git fetch --prune`.
- Le corps de la PR ferme son issue avec le mot-clé anglais `Closes #<n>` (GitHub ne reconnaît pas « Ferme #<n> », et le mot-clé n'agit que pour une PR qui cible `master`). Une PR qui ne traite qu'une partie de l'issue écrit `Refs #<n>`.
- Relectures, dans l'ordre de « Model routing » ci-dessous : `reviewer`, Antigravity, CodeRabbit, `@codex review` (facultatif, jamais bloquant : voir les conditions de fusion ci-dessus). Ne pas pousser de correction pendant qu'une relecture (Antigravity, CodeRabbit, Codex) tourne encore : celle d'Antigravity se lance en arrière-plan (quelques minutes) et se juge sur sa sortie, pas sur son code de sortie (le nettoyage du dossier temporaire peut le mettre à 1 alors que la relecture est complète) : elle approuve quand sa réponse finale dit clairement que rien ne reste, et une sortie vide ou tronquée se relance ; celle de CodeRabbit se lit avec `gh api --paginate` (chemins entre guillemets : PowerShell lit `{owner}` comme un bloc de script) sur `repos/{owner}/{repo}/pulls/<n>/reviews`, `repos/{owner}/{repo}/pulls/<n>/comments` et `repos/{owner}/{repo}/issues/<n>/comments` (résumé, « Review skipped », limite de débit). CodeRabbit ne relit pas seul ce dépôt (moins de 10 étoiles : « Review skipped ») : l'agent le déclenche par un commentaire (`gh pr comment <n> --body "@coderabbitai full review"`) une fois la tête stable. L'agent vérifie chaque remarque à la source avant de l'appliquer, répond sur chaque fil (correction et commit, ou raison de ne pas corriger) puis le résout. Juste avant de fusionner, l'agent relit `gh pr view <n> --json headRefOid --jq .headRefOid` et vérifie que `reviewer`, Antigravity et CodeRabbit portent sur ce SHA (pour `reviewer` et Antigravity, le SHA relu figure dans la note que l'agent a laissée sur la PR ; pour CodeRabbit, c'est le `commit_id` de sa relecture dans `repos/{owner}/{repo}/pulls/<n>/reviews`) ; une relecture sur un autre SHA, ou sans SHA, est relancée, sauf pour `reviewer` et Antigravity si le patch-id de leur SHA, recalculé à ce moment contre `headRefOid`, est égal (règle sur le rebase ci-dessus) ; CodeRabbit porte toujours sur `headRefOid`. Une fois toutes les conditions de fusion ci-dessus réunies sur le même commit, l'agent fusionne sans attendre un nouveau feu vert de Loïc, sauf dans les cas qui lui reviennent.

## Model routing

- Le modèle principal est l'alias `sonnet` (`.claude/settings.json`), résolu par la version de Claude Code installée (garder Claude Code à jour : `claude update`). Le fil principal est celui qui coûte le plus en tokens : Opus n'intervient que dans des subagents (`architect`, `reviewer`, et la relance `model: opus` après deux échecs, plus bas). L'alias `opusplan` n'est pas pris en charge dans nos sessions. Les subagents de `.claude/agents/` portent le modèle adapté à leur rôle (`explorer` Haiku, `implementer` Sonnet, `architect` et `reviewer` Opus). Ne pas forcer un modèle unique avec `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`.
- Toute tâche qui touche une migration, l'authentification, les secrets, la concurrence ou un invariant passe par `architect` avant `implementer`.
- Après deux échecs de test sur la même tâche, relancer avec `model: opus` au lieu de réessayer à l'identique.
- Toute PR passe d'abord par `reviewer`, puis par la relecture Antigravity (lancée par l'agent avec `review.sh` du skill `antigravity` ; en session cloud, où le skill et la CLI manquent, Loïc la lance et colle le résultat), CodeRabbit (déclenché par l'agent avec `@coderabbitai full review`), et `@codex review` en dernier (facultatif, jamais bloquant : voir les conditions de fusion ci-dessus).
- Les recherches larges en lecture seule vont à `explorer`, pas au modèle principal : recherche d'un motif dans le code, vérification d'une remarque de relecture contre la doc officielle ou le code (étapes 4 et 5 de `docs/agents/review-checklist.md`).
- Règle de Loïc (2026-10-17) : les modèles Claude (Anthropic) sont réservés à Claude Code — le fil principal et les subagents de `.claude/agents/` sont les seuls à consommer l'abonnement. Tout agent qui tourne dans un autre harnais (OpenCode, scripts, bots, CLI tierce comme Antigravity) ne lance jamais un subagent sur un modèle Claude payant : il utilise le modèle par défaut de son harnais (OpenCode : le modèle de session gratuit) ou un modèle d'un autre fournisseur. Avant de créer un subagent hors Claude Code, vérifier le modèle demandé.
- Règle de Loïc (2026-10-17) : la relecture ne tourne pas sur le même modèle que celui qui a écrit le code. En OpenCode, la passe `reviewer` (et tout subagent de relecture) prend un autre modèle gratuit de l'environnement que le modèle de session (ex. `opencode/nemotron-3.5-super-vl-free`), pour garder un regard différent de celui du modèle qui a écrit le code. Si l'environnement ne propose qu'un seul modèle gratuit — celui de la session — la relecture reste sur ce modèle gratuit et ne bascule jamais sur un modèle Claude ni sur un modèle payant d'un autre fournisseur ; la PR le consigne.

## Agent skills

### Issue tracker

Issues live in this repo's GitHub Issues, managed with the `gh` CLI. They track the development of Nexus itself; operational tasks will live in Nexus once it runs (ADR-012) — never mirror one into the other. See `docs/agents/issue-tracker.md`.

### Triage labels

The five default labels (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`). See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one `CONTEXT.md` and `docs/adr/` at the repo root. The decision log is still `DECISIONS.md` and the glossary is `docs/GLOSSARY.md`. See `docs/agents/domain.md`.
